# 型で不正な状態と扱い漏れを防ぐ

## 適用条件

型、関数の引数・戻り値、状態の表現を設計・レビューするとき。

## 判断の指針

型検査を、不可能な状態、意味の違う値の取り違え、分岐の扱い漏れを防ぐために使う。

- 状態の違いは判別可能なunionや値を持つenumなどで表す。完了フラグと任意の完了日時のような、矛盾した組み合わせを許す形を避ける。値から導出するか、状態を明示的に分ける。
- 許したい値から構造を組み立てる。空でない列は先頭と残り、時間区間は開始と長さとして表すなど、不正な値を作れない形を検討する。
- 同じ文字列でも利用者IDと注文IDを混同しないよう、意味を持つ専用の型を使う。生成時に検証し、以降は型を信頼する。
- JSON、RPC、IPC、CLI、環境変数、設定、DBからの値は、境界で解析するまで未検証の入力として扱う。
- 型検査を迂回するキャストや非null断言でごまかさず、検証、絞り込み、モデルの見直しで根拠を示す。避けられない危険な変換は局所化する。
- 新しい状態を追加した際、未対応の分岐をコンパイラが検出できるよう網羅性を確認する。
- 正式なスキーマがある形はそこから導出し、手書きの二重定義を作らない。
- 型を強めるのは、操作に未定義のケースが生じる場所に絞る。空の列の合計は0で定義できるが、先頭要素の取得には空でない保証が必要になる。

必要以上の型の精密さを目的にしない。型が減らす実際の扱い漏れや実行時の失敗を説明できることを基準にする。
