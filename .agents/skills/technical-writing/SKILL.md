# 読者が使える技術文書を書く

最初に読者、読後にできること、対象の版、出力先を決める。既存の文書構成・用語・テンプレートと依頼範囲を優先する。レビューだけならファイルを編集しない。

## 目的に合う構成を選ぶ

| 主な目的 | 構成と必要な内容 |
| --- | --- |
| 操作を通じて学ぶ | 作るもの、前提、実行する順序、各段階で見える結果。背景の説明は短くし、詳細へリンクする |
| 既知の目的を達成する | 適用条件、必要な準備、操作、条件による分岐、成功の確認と必要な復旧手順 |
| 仕様を調べる | 実際のAPI・設定等に対応する項目、型、既定値、制限、例外とエラー |
| 仕組みや理由を理解する | 問い、構成と動作、理由、制約、代替案と判断の根拠 |

READMEのような入口には複数の目的があってよい。節を分けて必要な詳細へ案内する。文書を形式に合わせるためだけに分割しない。設計書は目的・制約・採用案・代替案・未決事項を区別し、PR説明は問題と変更後の挙動、検証と制約から書く。

## 誤読を減らす

- 主要な結論や操作を先に置き、必要な理由・条件・根拠を続ける。
- 誰が何をするかを書き、条件や注意は影響する操作より前に置く。一文で複数の操作を詰め込まない。
- 一つの対象には同じ名前を使う。コード、コマンド、ファイル、UIの名前は実物と一致させる。読者に必要な専門語は初出で説明する。
- 「これ」「のみ」「または」の対象が曖昧なら名詞や条件を明記する。平易な語を選び、短縮によって前提や因果を失わない。
- 順番が必要なら番号、比較は表、独立した並列事項は箇条書きを使う。見出しとリンクの名前で行き先が分かるようにする。
- 手順の例には実行前提と期待結果を付ける。秘密情報や実データを埋めず、仮の値は仮と分かるようにする。

日本語に英語の語数・冠詞・大文字表記の規則を機械的に当てはめない。既存コード例のインデント、文体、用語規約を保つ。引用・法的文言・外部仕様の表記を推敲のために書き換えない。

## 根拠と完成を確かめる

数値、既定値、対応範囲、コマンドとリンクを対象のコード・設定・一次資料と照合する。実行が必要なら権限と環境を確認し、実行した対象と結果を記録する。例を書いただけで動作確認済みにしない。未確認・推測・将来の計画は、現在の事実と区別する。

構成が固まったら [unslop](../unslop/SKILL.md) で推敲し、仕様、否定、条件、確度、根拠が変わっていないことを読み返す。変更した文書と確認範囲を短く報告する。文書作成を理由にコミットや外部投稿まで行わない。
