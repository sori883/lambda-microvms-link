# 親・子の運用手順

## 登録する単位

unitは目的・担当範囲・完了条件を持つ仕事のまとまり。既存タスクを登録する場合は同じIDを使う。親も子もunitとして登録する。一つのunitが調査・設計・実装・検証等の複数工程を通れる。

成果物を独立して受け入れられ、担当・着手条件を分ける必要がある場合に子へ分割する。同じ担当で追える短い手順は計画内の項目にする。ファイル、工程、PR、エージェントの数だけunitを増やさない。

- 小規模な子は台帳内の目的・条件・報告で追い、task.mdを新規作成しない。
- 中規模以上は担当がtask.mdを用意し、既存資料や設計・証拠へつなぐ。新規保存先の既定は利用先の`.space/tasks/<unit-id>/task.md`。
- 大規模な親は独立したplan.mdに分担と統合の計画を書く。
- 台帳を導入したunitの最新状態はCLIを正本にする。task.mdの状態・工程表は台帳参照へ置き換え、手書きで二重更新しない。

## 親が準備すること

依頼範囲、共通設計、終了地点、作業の所有範囲、必要な検証と納品を確認する。台帳の既定配置は利用先の`.space/tasks/.orch/`。既存の台帳がある場合は読み、初期化で置き換えない。

親unitと必要な子unitを登録する。作業担当`owner`、進捗の記録担当`recorder`、確認を記録できる担当`verifiers`を指定する。recorderを省略するとownerが記録する。小規模な子の記録を親が代行するときはrecorderを親にする。

依頼を終了する条件と対象を評価する条件を区別する。レビューだけなら「指摘・根拠・限界を報告した」が終了条件であり、対象コードが不合格でも報告を完了できる。修正まで依頼されている場合は必要な修正・検証の合格も終了条件にする。

依存には先行unitと必要な成果物を示す。既定では現在の提出が親に受け入れられていることを求める。合格が必要な場合は条件IDと期待判定も指定する。未マージのコードを利用できるか、必要な環境・権限があるかは親が実際に確認する。

## 分担して実行する

1. `unit ready`で候補と不足を見る。同じファイル・DB・環境を同時に変更しないよう所有範囲を確認する。CLIは範囲の意味やglobの重なりを判定しない。
2. 環境で許可された道具で担当を起動する。目的、入力、書き込み範囲、完了条件、確認方法、unit ID、台帳の場所、担当ID・セッション、attempt、報告先を渡す。他担当の変更を戻さないことも伝える。
3. 子は`unit get`で現在のversion・attemptを取得して`unit start`する。工程や次の判断が変わる節目に更新する。毎コマンドの記録は不要。
4. 確認担当は実際の結果を`ledger record`する。未実行はunknownとし、予定の証拠を取得済みにしない。
5. 子は工程の終了状態を記録し、成果物・証拠・限界を`unit submit`する。完了状態と通知は同時に保存される。保存に失敗した場合は完了済みと報告しない。
6. 親は`inbox list`で通知を読み、成果物と証拠を照合して`unit accept`または`unit return`する。子のcompletedと親のacceptedを区別する。

最初の子を引き渡しまで通し、指示・証拠・受け渡しの不足を直してから残りへ展開する。並列実行を使えない場合は同じ単位を順次進める。

## 待ち・差し戻し・引き継ぎ

判断が必要ならgateへ問い・選択肢・推奨案・回答者を記録し、親が人間へ質問する。回答待ちになるunitだけを止める。既定案や時間経過を回答・承認の代用にしない。回答の根拠を`gate resolve`で記録し、内容が契約や設計を変える場合は対象unitの条件も更新する。

通常の再開は契約・入力版が同じ場合の`start`。版が変わった場合は、中断して`reopen`で新しい試行を作る。旧試行の合格を自動的に流用しない。再利用する証拠は現在も適合する理由を確認し、新試行の確認記録へ出典付きで記録する。

新しい試行を作ると、旧提出と未処理の完了通知は現在無効として履歴に残る。再提出前に後続の提出があるとは記録しない。差し戻し・やり直しの理由を残し、親は履歴も必要に応じて読む。

担当交代は旧担当の書き込み終了を確認し、`assign`でセッションと試行を切り替える。停止の根拠を用意する。統括担当の新セッションが最初に実行する引き継ぎには[CLIの引き継ぎ条件](cli.md#セッションの引き継ぎ)を使う。通常更新のsession照合を無効化しない。

CLIの担当照合は同じプロジェクト内の誤更新を防ぐ。根拠ファイルが存在することだけで停止・権限・判断の正しさを証明したことにはしない。引き継ぎ後に旧担当が実際のコードへ書き込まないことは、親が実行環境でも確認する。

## 統合と引き渡し

親は子の受け入れに加え、統合後の実物と全体の条件を確認する。子の件数だけで親を完了にしない。中止した子を完了条件から外す場合は、範囲変更の理由と元の条件をどこで扱うかを明記する。

親を持たないルートunitは、統括担当が最終成果物を照合してacceptする。統括担当が作業も担当した場合は自身の提出を受け入れる。この操作は引き渡しの確認であり、独立したレビューの代わりにはしない。必要なレビューは別の確認担当に依頼する。

必要なverify・review・deliverへ結果を渡す。システムの設計・構成・重要な歴史の保存候補はdeliverが整理し、OKFスキルで検索・保存・検証する。台帳や試行の履歴をそのままOKFへ移さない。

中断・引き継ぎの要約が必要ならcheckpoint-safelyを使う。台帳の場所・参照時点・unit ID・成果物・次の操作を渡す。通常の進捗更新でcheckpointを増やさない。

一覧をファイルとして残す場合は`export`する。TSVとstatus.mdはその時点の出力であり、編集して最新状態を変更しない。
