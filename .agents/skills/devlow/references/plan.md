# 計画

## 目的

採用した設計と完了条件を、担当が実行・検証できる作業単位へ分ける。順序、依存関係、書き込み範囲、検証方法・必要な証拠・取得条件と引き渡し条件を定め、今回着手できる範囲を明確にする。

## 開始時に必要なもの

- 依頼の目的・範囲・終了地点、受け入れ条件、既存の承認と制約。
- 採用または再利用する設計の利用例・骨組み・不変条件、対象の版、未決事項。
- 調査・試作の根拠、変更対象、既存の検証方法・実行環境。
- 既存のタスク・計画・進捗、親の共通条件と利用可能な担当・道具。

既存資料を参照し、同じ調査や設計を複製しない。設計の採用状況と実装状況を区別し、計画を作ること自体は実装着手や完了の証拠にしない。

## 手順

### 1. 今回の終了地点と前提をそろえる

今回渡す結果と、計画に含める作業を確認する。計画のみの依頼は計画の確認・引き渡しまでとし、実装も依頼されている場合は既存の承認を引き継ぐ。

作業順序や実現性を左右する事実の不足は [調査](investigate.md)、構造・互換性の未決は [設計](design.md)へ戻す。必要な試作の結果を参照し、仮説を確認済みの前提にしない。後続だけに関係する未決事項には、解決方法・担当・その結果を待つ単位を記し、独立して進められる範囲を分ける。

### 2. 検証できる作業単位に分ける

一つの変更結果と、その結果を確かめる方法・取得する証拠を単位にする。実装・検証・必要なレビューを対応付け、作業名だけの一覧にしない。ファイルごと・工程ごとに自動分割せず、同じ不変条件を一緒に変える必要がある範囲は一つの担当へまとめる。

各単位に、結果、関係する受け入れ条件、入力となる設計・成果物、変更するファイルやモジュール、完了条件を記す。標準以上では既存のIDを優先し、なければ計画内で追える単位IDを付ける。単位IDを付けるだけで子タスクやPRを作らない。

独立した成果物・担当・引き渡しが必要な範囲は子タスクへ分ける。同じタスクで追えるものは計画内の項目でよい。PRやコミットで納品する依頼ではその境界も示すが、一単位を一PRへ固定しない。

### 3. 依存関係・担当・書き込み範囲を定める

複数単位の計画では、次の四つを確認して記録する。該当しないものにも短く理由を残す。

| 観点 | 決めること |
| --- | --- |
| 先に終える作業 | 共通の契約・基準測定・環境準備など、後続を始める前に必要な成果物と成立条件 |
| 独立して進める範囲 | 別々に変更・検証できる単位と、同時に進めてよい条件 |
| 共有する書き込み先 | ファイル・台帳・DB・テスト環境等の共有。分離できるものは分け、分けられない不変条件には単一担当または実行順を設ける |
| 分割の大きさ | 安全に引き渡せる最小のまとまり。一人でまとめる場合も、結合度や検証の都合など理由を示す |

依存は「U-1の後」だけでなく、どの成果物がどの条件を満たせば着手できるかを示す。コード依存では参照する版・ブランチ等も分かるようにし、未マージの変更を使えるかは実際の作業方式から決める。存在しない依存先・自己参照・循環や、完了条件に結び付かない作業がないか確認する。

各単位の担当と変更可能な範囲を決め、同時に同じファイルへ書く担当を重複させない。共通ファイルは所有する担当へ変更を集約するか、書き込み終了を確認して引き継ぐ。担当がまだ未割当なら、割当を着手条件として残す。子を使う場合の指示と受け渡しは [全体フロー](workflow.md#6-複数タスクを管理する)に従う。

大規模では全体の依存と納品単位を示し、直近で着手する範囲から詳細を決める。最初の一単位を検証・引き渡しまで通す計画にし、その結果を後続へ反映する時点を置く。詳細が未確定の単位を着手可能とは扱わない。

### 4. 検証方法・必要な証拠と引き渡し条件を決める

受け入れ条件ごとに、担当する単位、検証方法、期待値・合否条件、必要な証拠、取得する対象・環境・時点を対応付ける。単位ごとの確認に加え、複数単位を組み合わせた後の全体確認も計画する。確認可能性は既存のコマンド・設定・資料から確かめ、未実行の方法を動作確認済みと書かない。

予定の証拠は未取得と明記し、存在するログや画像への参照にしない。取得済みの基準測定等は対象・時点を添えて参照できるが、変更後の結果とは区別する。実行後の結果・証拠・判定はtask.mdやverification.mdへ記録し、この計画と対応付ける。

| 確認の種類 | 計画に含める条件と内容 |
| --- | --- |
| 局所・回帰 | 変える振る舞いと保つ振る舞い。意味のあるテストや形式検証を選び、不具合なら変更前の失敗と変更後の同じ確認を対応付ける |
| 実際の利用経路 | UI・CLI・外部連携等の挙動を変える場合は、実際の操作・入力・出力・最終状態を確かめる方法を示す。文書・スキルはリンクや形式に加え、必要な利用例で内容・判断の妥当性を確認する |
| 性能 | 性能改善や性能条件がある場合は、指標、同じ条件の変更前後の測定、合否基準を定める。基準値が未取得なら、変更前に測る先行作業を置く |
| 移行・失敗時 | データ・互換性・復旧に影響する場合は、移行中・失敗時の状態、戻せる範囲と戻せない操作、再開条件を示す |

該当しない検証は理由を示す。方法や合否条件が未確定の場合は、それを決める単位を先行させる。異なるシナリオ同士の性能比を成功条件にせず、新規機能なら追加処理や最終状態の絶対的な基準を用いる。

全体フローで必要とされたレビューについて、対象・時点・担当と、次へ進む条件を計画する。確認手段や権限が不足する場合は影響する単位と不足を示し、弱い代替手段で必須条件を満たしたことにしない。実装、レビュー、公開等の区切りと、それぞれの既存承認の範囲を対応付ける。

### 5. 更新責任と計画変更の扱いを決める

計画本文の更新担当と、作業進捗の正本・更新先を明示する。[全体フローの更新責任](workflow.md#進捗の更新者)に従い、単独ならその担当、親子に分かれる場合は子が自身の進捗、親が受け入れ確認と全体計画を更新する。独立記録を持たない小規模な子は親へ報告する。

CLIの台帳や子のtask.mdが進捗を持つ場合、計画には参照と確認時点の集約を置き、別の最新状態を二重管理しない。道具が利用できない場合の管理は全体フローに従い、架空のコマンドや台帳ファイルを計画の前提にしない。

範囲・設計・依存・担当・検証条件が変わったら、記録担当が理由と影響する単位を更新し、関係する担当へ引き継ぐ。条件が変わった証拠は再利用できるか見直す。完了済みの履歴や変更前の結果を消さず、関係しない単位はやり直さない。

### 6. 計画を照合して渡す

受け入れ条件に対応する作業・検証方法・必要な証拠の計画に漏れがないか、依存の矛盾、書き込み担当の重複、着手前に必要な判断がないか確認する。実行する最初の単位とその前提を示し、未決事項があれば進められる範囲を明記する。必要なレビュー結果も計画へ反映する。

計画のみの依頼は、計画・確認結果・未決事項を [引き渡し](deliver.md)へ渡して終了する。実装も依頼され、対象範囲の着手条件が満たされていれば [実装・編集](implement.md)へ進む。ユーザーが実装前の確認を指定している場合は計画を提示して待ち、既存の承認がある範囲では確認を繰り返さない。

## 成果物

小規模は会話に次の操作と確認方法を短く残し、task.mdやplan.mdを一律に作らない。必要な判断は既存の関連資料へ残す。

標準は通常task.mdに計画をまとめる。独立して共有・レビュー・更新する場合は同じディレクトリの `plan.md` に分け、task.mdから参照する。大規模の親は全体計画を独立したplan.mdに置き、子の記録を参照する。新規の既定は `.space/tasks/<task-id>/plan.md`。[計画記録のひな形](../assets/plan-template.md)は必要な節だけ使い、既存の計画があれば更新・参照する。

子タスクの指示は既存の記録方式で渡し、単位ごとのbrief.md等を一律に増やさない。読み取り専用の場合は計画も回答にまとめる。作業順序・担当・未完了の項目はタスク側に保持する。確定したシステム設計・判断があれば、全体フローの保存条件に合う候補と根拠を引き渡し工程へ渡し、OKFへの保存は任せる。

## 終了条件

- 依頼範囲と受け入れ条件に、作業単位・担当範囲・検証方法・必要な証拠が対応している。
- 依存、共有する書き込み先、進捗更新の責任、レビューと引き渡し条件を追える。
- 着手する範囲の前提と担当・合否条件が確定し、後続の未決事項と解決方法が明確である。

計画のみの依頼では不足や前提待ちを明記した計画を渡せるが、その範囲を実行可能とは扱わない。計画作成の完了と計画内の作業完了を分け、実施して証拠を得るまで作業項目を完了にしない。

## 短縮・再利用・省略の扱い

既知の一作業なら「変更すること・確認すること・次の操作」へ縮める。既存の計画は対象・版・依存・承認への適合性を確認し、差分だけ更新する。大規模の子は共通計画を参照し、担当範囲の詳細だけを追加する。工程の採否は全体フローに従う。

## 失敗時の戻り先

目的・範囲・完了条件の変更は [依頼整理](intake.md)、根拠や測定方法の不足は調査、骨組みや互換性の矛盾は設計へ戻す。依存の循環・担当の重複・検証できない粒度は関係する単位を組み直す。必要な前提がない場合は依存する範囲を待ちにし、解決方法と独立して進められる単位を残す。
