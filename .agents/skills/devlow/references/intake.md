# 依頼整理

## 目的

依頼を、次の担当が目的・範囲・受け入れ条件を理解して着手できる形へ整理する。今回渡す成果物と終了地点を定め、未決事項は次の工程を妨げるものと、その工程で解消するものに分ける。

## 開始時に必要なもの

- 今回の依頼と、それまでの追加条件・訂正・既存の承認。
- 作業対象のプロジェクトと、利用先で適用する指示。
- 依頼で指定されたIssue、設計資料、対象ファイル等。指定がなければ、対象の特定に必要な範囲だけ確認する。
- 続きの作業なら既存のタスク記録、成果物、必要なcheckpoint。

不足する資料を架空の参照で補わない。元の依頼を参照できるURLやIDがなければ、依頼の要旨と確認時点を記す。記録と現在の対象が食い違う場合は、差分を確認してから再利用する。

## 手順

### 1. 依頼と既存の決定を読み取る

求められている結果を一文にし、提案された方法と分ける。方法が指定された制約なのか、検討用の候補なのかを確認する。現在の依頼で訂正された箇所は更新し、引き続き有効な条件・承認は引き継ぐ。

対象ファイルや成果物の有無を確かめ、既存の記録で目的・範囲・条件が分かるならそこを更新する。依頼整理のためだけにシステム全体の調査や設計を始めない。追加の現状調査が必要なら、何を調べれば判断できるかを次の工程へ渡す。

### 2. 今回の範囲と終了地点を定める

対象、含める作業、境界に関わる対象外、制約、渡す成果物を記す。終了地点は [全体フロー](workflow.md) の依頼種別に照らして選ぶ。例えば設計資料の作成と、その設計を実装する仕事は区別する。

対象外の一覧を網羅的に作らず、誤解や範囲拡大を防ぐために必要なものに絞る。ファイルの詳細な所有範囲や実装の方式は、ここで分からなければ調査・設計・計画へ渡す。既存の承認で進められる作業に、新しい承認段階を一律に追加しない。

### 3. 受け入れ条件を確認できる表現にする

「何がどうなれば今回の依頼を満たしたと判断できるか」を成果物や振る舞いで記し、確認方法を対応させる。標準以上では条件IDを付け、小規模は短い文章でよい。既存の条件IDがあれば保持する。

例えば設計のみなら「対象と責務、採用理由、未決事項を資料から追える」、不具合修正なら「報告された操作で問題が再現しなくなり、維持すべき挙動を確認できる」とする。「実装する」「テストする」だけを達成条件にしない。

検証・レビューのみなら「指定した対象の確認結果と限界を報告する」等を依頼の終了条件とし、対象を評価する条件を別に識別する。依頼の完了を対象の合格や修正完了と同じ条件にしない。

具体的なコマンド・閾値・計測環境が不明なら、決める工程と必要な情報を残す。ユーザーが指定していない数値や品質条件を確定事項にしない。条件の候補は確定した条件と区別し、その候補を満たしたことだけで後に完了を判定しない。

### 4. 未決事項を分ける

| 未決事項 | 扱い |
| --- | --- |
| コード・資料・観測で分かる事実 | 必要な範囲を確認するか、問いと調査先を調査工程へ渡す |
| 成果物や許可範囲を左右する、根拠から決められない好み・方針 | ユーザーへ確認する。どの作業が回答に依存するかを残す |
| 調査・設計・計画で決める詳細 | 決める工程と、それまでに分かっている制約を残して先へ進む |

仮置きできる解釈は、根拠と影響を短く示して進める。回答待ちの事項は仮置きで承認されたことにせず、回答に依存しない作業を分ける。未決事項があるという理由だけで、依頼整理や全体作業を止めない。

### 5. 工程と記録の形を選ぶ

全体フローの規模・リスク・依頼種別の条件から、各工程を実施・統合・再利用・省略に分ける。選択と理由、再利用する資料、最初に着手する作業を記録する。選択条件そのものをこの工程で追加しない。

依頼の進行状態と、確認対象の成果判定を[全体フロー](workflow.md#状態と完了の判定)に従って分ける。工程表にも実行状態と確認結果を別々に記す。確認していない対象は未確認とし、依頼整理の終了だけで依頼全体を完了にしない。

小規模は複数工程を一行にまとめてよい。複数担当や独立した納品単位が必要なら、親子に分ける必要と共有する条件を示し、具体的な分割は計画工程へ渡す。依頼整理だけで全子タスクや台帳を作り切らない。

全体フローで確認した原則・ルールと未確認事項を引き継ぎ、依頼整理中に対象や段階が変わった場合だけ、必要な参照を追加する。

## 成果物

成果物は、次の内容を含む依頼整理記録とする。短い内容は一つにまとめる。

| 内容 | 記録すること |
| --- | --- |
| 依頼と目的 | 元の依頼、期待する結果、既存の決定への参照 |
| 範囲と終了地点 | 対象、今回含める作業、必要な対象外、制約、成果物 |
| 受け入れ条件 | 達成を判断する内容、確認方法または決める工程。標準以上は条件ID |
| 工程の選択 | 種類・規模・リスクと理由、工程の選択、再利用する資料、実行状態と確認結果 |
| 進行状態と成果判定 | 依頼の現在の状態、対象の判定と根拠・未確認の範囲への参照 |
| 未決事項と次の操作 | 何が未決か、影響する作業、解決方法、今着手できる具体的な一手 |

全体フローに従い、標準（中規模）・大規模ではtask.mdを作成・更新する。新規の既定は `.space/tasks/<task-id>/task.md`。小規模は会話に短くまとめ、task.mdを新規作成しない。既存タスクへの追加指示なら同じ記録を更新する。[タスク記録のひな形](../assets/task-template.md)から必要な項目を使い、既存ファイルをひな形で上書きしない。

依頼整理を独立してレビュー・共有する必要がある場合だけ、task.mdと同じディレクトリの `request.md` に分ける。新規保存先の既定は `.space/tasks/<task-id>/request.md`。task.mdには要約と参照を置く。短い依頼に両方を作らない。作業中の依頼整理記録はOKFへ登録せず、checkpoint作成もこの工程の必須処理にはしない。

## 終了条件

- 目的・範囲・今回の成果物と終了地点が分かる。
- 完了を判定する条件が記され、確認方法が不明なものは決める工程が分かる。
- 次に進む工程と最初の操作が選ばれ、その操作を妨げる未解決事項がない。
- 残る未決事項の影響と解決先が分かり、必要な記録を次の担当が参照できる。

依頼整理のみの依頼なら、この記録を渡して終了する。後続作業も依頼に含まれていれば、全詳細の確定や再承認を待つ工程を追加せず、選んだ作業へ進む。

## 短縮・再利用・省略の扱い

- 明確な小規模依頼は、対象・終了条件・確認方法・次の操作を会話に短くまとめる。判断・設計の資料を残す場合も、それだけを理由にtask.mdを新規作成しない。
- 読み取り専用なら記録のための書き込みも行わず、必要な整理を回答へ含める。
- 既存の依頼整理を再利用するときは、今回の対象・版・指示との一致を確認し、変わった箇所だけを更新する。
- 子タスクは親の共通条件を参照し、自分の目的・担当範囲・条件と差分を確認する。親と同じ本文を複製しない。
- 依頼整理自体は省略せず、明確な依頼では他の工程へ統合する。

## 失敗時の戻り先

対象を特定できない、指示が矛盾する、次の操作の許可範囲を決められない場合は、該当する範囲を進めず、必要な確認と独立して進められる作業を示す。資料の取得失敗は確認済みに置き換えない。

後続工程で目的・範囲・受け入れ条件の前提が変わったら、この記録の該当箇所を更新し、理由と影響を残す。実装上の詳細が判明しただけなら、担当する工程で処理する。保存が必要なのに失敗した場合は、整理した内容を回答に残し、保存できた範囲と引き継ぎ上の不足を区別する。
