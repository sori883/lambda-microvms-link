# 設計

## 目的

依頼の完了条件と調査結果から複数の構造を探索し、比較・統合した設計と、その選択理由を定める。利用例から実装の骨組みを導き、次の計画・実装へ渡す。設計だけの依頼では今回決めた範囲を成果物として渡す。

## 開始時に必要なもの

- 依頼の目的・範囲・完了条件、既存の承認と制約。
- 調査で確認した現状・根拠・未確認事項、適用する原則・設計判断。
- 再利用する設計やブループリント、親から渡された共通条件。

資料の対象・版・適用条件を確認し、既に決まっている内容は引き継ぐ。現状を説明するブループリントと、採用済みでも未実装の設計を区別する。

## 手順

### 1. 現状を理解し、共通の設計課題を定める

接続する既存システムの責務・処理経路・データ所有・制約を根拠付きで把握する。調査済みの同じ対象・版のモデルは再利用し、不足があれば [how](../../how/SKILL.md)へ渡す。責務の所有や層構造を変える場合は、既存の理由も確認し、不足を [why](../../why/SKILL.md)へ渡す。ファイル名の列挙だけでは現状を理解したことにしない。接続する既存システムがない新規開発では、その理由を残して現状調査を省ける。

変更前後の代表的な利用例と完了条件、設計対象、保つ互換性・制約を候補に共通の入力としてまとめる。依頼整理の全文を複製せず、根拠・対象の版・未確認事項を参照する。比較する担当は、条件への適合、利用側へ露出する複雑さ、変更・移行への影響などから、今回判定できる評価基準を先に決める。要件・制約は全候補に渡し、採点表は比較側で使う。

### 2. 構造の異なる候補を独立に作る

全体フローで新しい構造の探索が必要とされた場合は、最初の案が十分に見えても、統合前に最低2案を作る。責務の置き方、データ所有、処理・連携方式などが異なる案を比較する。命名や引数の差だけでは別の構造に数えない。

利用環境で許可された子エージェントを使える場合は、同じ課題と根拠を渡して並行に探索する。利用可能な設定に従い、異なる観点やモデルを使える場合は活かす。固定のモデル名を前提にしない。各担当は自分の候補だけを所有し、他候補を読んで折衷したり、共通の設計記録・実装を編集したりしない。共有作業場所では他担当も作業していることを伝え、他者の変更を戻させない。

子エージェントや並行実行を使えない場合は、同じ担当が異なる構造を順に作り、その制限を記録する。案数を減らしたり、独立した複数担当による探索と報告したりしない。候補の不足・失敗・同じ構造への収束があれば、同じ要件・制約の下で別の責務配置や連携方式を探索して不足を補う。比較の結果、一案だけが採用可能でもよい。異なる2案を用意できない場合は探索未完了とし、その理由を残す。

各候補は、まず利用側がどう使うかを書き、そこからデータ構造・型・関数のシグネチャ・モジュール境界を導く。実装本文は未実装の骨組みや擬似コードでよい。通常は設計資料内のコード例とし、設計だけの依頼で稼働コードへ未実装の本体を追加しない。

| 設計で変えるもの | 決める内容 |
| --- | --- |
| 操作・API・コマンド | 利用例、入出力と型・シグネチャ、正常時と失敗時の振る舞い |
| 構成要素・連携 | 責務と依存の方向、処理・データの流れ、境界の検証と不変条件 |
| 永続データ・互換性 | データの所有、同時更新・再実行、互換性、移行中の扱いと戻し方 |
| 文書・スキル | 読者の利用例、適用条件、入力と成果物、参照先と責務。型の代わりに文書・指示の構成を示す |

今回関係する内容だけを具体化し、各候補の理由、受け入れる不利益、検討して退けた別の構造も短く添える。ファイルの詳細な所有範囲、作業順序、担当割り当ては計画工程へ渡す。

### 3. 候補を比較し、一つの設計へ統合する

候補が出そろってから、設計をまとめる担当が全候補の本文を読み、同じ評価基準で比較する。次の問題があれば、統合前に該当案を修正または見送る。

- 公開操作が多い割に処理を隠せず、利用側が内部の手順を組み立てる必要がある。
- 内部表現・通信形式・保存形式の判断が複数箇所へ漏れ、一つの変更に連動修正が必要になる。
- 知識や責務の所有より実行順だけで分割し、同じデータと条件が複数の境界に重複する。
- 方針・変換・抽象化を持たず、同じ引数を次へ渡すだけの層が増える。

小さな公開面に必要な機能を収め、利用側が知らずに済む複雑さを増やせる案を評価する。単なる呼び出し階層の深さや実装行数を良さの指標にしない。

利用環境で許可される場合は、候補作成に参加していない読み取り専用の比較担当にも、候補ID・本文・評価基準を渡す。親の暫定的な採用案は渡さず、親も並行して評価する。判定が分かれたら根拠と基準の曖昧さを確認して結論を記録する。比較担当を使えない場合は自己評価と明記し、全体フローで必須とされた独立レビューの代用にはしない。

最も適合する案を土台に選び、他候補の有効な部分だけを、その境界・不変条件と両立するよう取り込む。候補同士を機械的につなぎ合わせない。土台と理由、取り込んだ内容と出典の候補ID、見送った内容と理由、比較担当の結論または未実施、候補の不足・失敗を残す。取り込む内容がなければ、その判断を明記する。

### 4. 未知と統合後の整合性を確認する

事実の不足は [調査](investigate.md)へ戻し、好み・方針が結果を左右して根拠から選べない場合は人間へ確認する。既存の回答・承認で決められる内容を再確認しない。

観測で比較できる未知は、依頼と権限の範囲で必要な試作・計測を行う。対象、条件、結果、採否への影響を残し、試作の成功を本実装の完成や運用上の保証に置き換えない。比較前に必要な観測は先に行う。前提が変われば、影響する候補の探索・比較をやり直す。

統合後の案を、利用例・完了条件・評価基準・型や境界の整合性で改めて確認する。候補が単独で成立していても、統合案が成立するとは限らない。問題が取り込み方にあれば統合を直し、共通の前提にあれば調査・探索へ戻す。全体フローで必要とされた独立レビューを行い、結果と残件を反映する。対象の版、確認した内容、未確認の範囲を残し、設計の確認と実装後の検証を区別する。

### 5. 採用案と骨組みを次へ渡す

利用例と整合する骨組み、統合理由、維持する条件、検証すべき振る舞い、残る問いを [計画](plan.md)・実装へ渡す。未決事項が次の作業を妨げるかを分け、進められる範囲を示す。実装担当は採用した骨組みを基準に具体化し、境界・不変条件の変更は理由を示して設計へ戻す。

ユーザーが実装前の確認を求めた場合は、統合案を提示して待つ。それ以外は既存の依頼と承認の範囲で次へ進み、設計工程だけを理由に承認を取り直さない。設計の採用を、依頼に含まれていない実装・公開等の承認として扱わない。

## 成果物

候補の構造、共通基準による比較、統合後の利用例と骨組み、採否・取り込みの理由、根拠、確認結果と未決事項をまとめる。採用状況と実装状況は別に示す。

標準以上は通常task.mdへまとめる。独立して共有・レビュー・再利用する場合は、同じディレクトリの `design.md` に分け、task.mdから参照する。新規の既定は `.space/tasks/<task-id>/design.md`。[設計記録のひな形](../assets/design-template.md)は必要な節だけ使う。既存の設計があれば、その資料を更新・参照する。

複数担当が候補を書き出す場合は、タスクの記録先を基準に `design-candidates/<round-id>/<candidate-id>.md` へ分け、各担当は割り当てられた候補だけを書く。候補内に利用例・骨組み・理由をまとめ、比較・統合結果は設計の記録担当がtask.mdまたはdesign.mdへ書く。再探索では新しいround-idを使って前の候補を残す。候補ごとにtask.mdを増やさない。単独で順に比較する場合は同じ設計記録の節へまとめてもよい。

小規模はtask.mdを新規作成せず、必要な判断・設計だけを関連資料へ短く残す。候補を分ける場合も関連する設計資料の隣へ置く。読み取り専用なら候補・比較も回答にまとめ、保存は行わない。途中の候補はタスク側に保ち、採用した設計の内容・統合理由と重要な代替案の採否を、[全体フローの保存条件](workflow.md#okfに残すシステムの設計と歴史)に合うdecisionの保存候補として識別する。対象・根拠・採用状況と実装状況を添えて [引き渡し](deliver.md)へ渡し、OKFへの保存・更新・検証は引き渡しに任せる。

将来案は設計資料に置き、現在のブループリントを書き換えない。実装後に確認できた構成の文書化が必要になったら、引き渡し工程から [system-blueprint](../../system-blueprint/SKILL.md)へ渡す。既存の構成や設計理由を理解するためのOKF検索・参照は、設計中も行ってよい。

## 終了条件

- 今回の完了条件に対応する設計内容と選択理由を説明できる。
- 新しい構造の探索が必要な場合は、構造の異なる最低2案、比較結果、統合理由と統合後の確認がある。再利用・短縮の場合は対象・版・理由が分かる。
- 依頼に応じた設計の確認・必要なレビューを行い、結果と残件が分かる。
- 計画・実装へ進む範囲では、振る舞い・境界を決められない未決事項が解消されている。

設計だけの依頼では、求められた範囲の案・比較・結論と未決事項を [引き渡し](deliver.md)へ渡して終了できる。案の比較だけを求められた場合は採用・統合を強制しない。探索や必須レビューが未完了なら、その報告を条件充足や実装への引き渡しと扱わない。採用済みの設計でも、実装や効果が未確認ならその状態を明記する。

## 短縮・再利用・省略の扱い

小規模で方法が既知なら、変更前の確認に設計を統合する。既存設計は今回の対象・版・条件への適合性を確かめ、差分だけ扱う。大規模の子は親の共通設計を参照し、同じ候補探索を繰り返さない。ただし、担当範囲で新しい構造を決める場合や再利用できない前提変更があれば、その境界について複数案を探索する。規模や文章量だけを理由に案数を減らさない。工程の採否は全体フローに従う。

## 失敗時の戻り先

目的・範囲・完了条件を変える必要があれば [依頼整理](intake.md)、現状や根拠の不足は調査へ戻す。矛盾や指摘は関係する案を見直し、無関係な設計まで作り直さない。未決の方針や試作不能がある場合は、その影響・解決方法と独立して進められる範囲を残す。

実装中に同じ形の回避策が複数箇所で必要になる、型の抜け道や特別扱いが増える、利用側が内部規則を知る必要が生じるなど、骨組みに吸収できない問題が繰り返される場合は、設計自体を見直す。単発の不具合だけで全体を破棄しない。

見直しでは、実装で分かった事実を調査へ戻し、新しい制約として候補を再探索する。不要な責務や境界を減らせないか確認してから統合し直し、旧設計を置き換える理由と影響する計画・検証を更新する。「設計を捨てる」は、既存実装や他者の変更を自動削除する指示ではない。
