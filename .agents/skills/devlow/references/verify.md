# 検証

## 目的

現在の成果物が受け入れ条件を満たすかを、対象に合う方法と証拠で判定する。実施した確認、失敗、確認できなかった範囲を区別して、レビューまたは引き渡しへ渡す。

## 開始時に必要なもの

- 対象の成果物・差分と版、受け入れ条件、設計と計画にある検証方法。
- 再現手順、基準値、実行環境、必要な操作の権限。
- 既にある検証結果と証拠、未確認事項、担当と記録先。

小規模は会話の完了条件を使う。検証のみなら、報告を完了とする条件と、対象を評価する条件を区別する。検証方法が未確定なら、その場で決められるものを具体化し、設計や方針に依存する不足は担当工程へ戻す。

## 手順

### 1. 検証する対象を固定する

実際に確認するリビジョン・差分・設定・環境を記録する。未コミット変更がある場合はその差分と未追跡ファイルも識別し、HEADだけを証拠の対象にしない。ビルド済みのものを使う場合は、対象の変更を反映した生成物かを確かめる。

既存の証拠は対象・条件・環境との対応を確認して再利用する。後から変更された箇所や前提に依存する結果は未確認へ戻す。変更していない範囲まで理由なく全件やり直さない。

### 2. 条件に合う方法で確かめる

計画の期待結果・合否条件を実行前に確認する。観測結果に合わせて合格条件を緩めない。実施方法を変更する場合は理由と影響を残す。

| 対象 | 確認すること |
| --- | --- |
| コード・設定 | 変更した振る舞いと回帰、必要なビルド・型・形式確認。テストの成功だけで別の実経路を確認済みにしない |
| UI・CLI・連携 | 実際の入口から操作し、入力・出力・最終状態を確認する。必要な失敗時の動作や互換性も含める |
| 不具合・性能 | 修正前の再現と同じ条件での結果、同条件の基準値との比較。再現不能や比較不能はその限界を残す |
| 設計・計画・調査回答 | 根拠・対象の版、利用例や完了条件との整合性、依存・責務・未決事項。実装や稼働の証明とは分ける |
| 文書・スキル・配布物 | 参照先と形式、利用者が成果物を使えること、内容・判断の妥当性。配布する場合は配布先にない開発元ファイルへ依存しないかも確認する |

必要な確認を、原因を切り分けやすい順で実施する。実操作や保存を伴う確認は依頼と権限の範囲で行う。読み取り専用の依頼は根拠の照合で確認し、書き込みや実行が必要な検証を済ませたことにしない。

既存のプロジェクト用verifyスキルがあれば、今回の対象・版・条件に適合する手順を使う。再利用可能な検証手順の作成も依頼範囲なら [create-verification-skill](../../create-verification-skill/SKILL.md)、既存手順とアプリのずれを直す場合は [maintain-verification-skill](../../maintain-verification-skill/SKILL.md)へ渡す。単発の検証だけの依頼でスキル作成・更新を追加しない。

実行方法、期待値、実際の結果、対象の版・環境、証拠への参照を残す。プロセスが起動した、終了コードが0だったという事実が、利用者の求める最終状態まで示すかを確認する。

### 3. 結果と不足を分類する

| 判定 | 意味 |
| --- | --- |
| 合格 | 今回の対象に対して条件を満たす証拠がある |
| 不合格 | 条件を満たさない結果を確認した |
| 未確認 | 未実施、実行不能、結果が曖昧、対象・環境が一致しないなど、判定する証拠が足りない |
| 対象外 | 今回は条件が適用されない。理由を残し、合格件数へ含めない |

失敗が今回の変更によるものか、既存の問題か、環境・確認方法の問題かを根拠から切り分ける。無関係な失敗を消すためだけに範囲を広げず、満たせない必須条件は残す。再試行は条件の修正や新しい根拠がある場合に行い、成功するまで繰り返して不安定さを隠さない。

変更まで依頼されている場合、原因の不足は [調査](investigate.md)、構造の矛盾は [設計](design.md)、方法や範囲の不足は [計画](plan.md)、変更の不備は [実装・編集](implement.md)へ返す。検証のみの場合は、問題と必要な対応を報告に含め、対象の修正へ進まない。受け入れ条件自体の変更は依頼整理で合意し、検証担当だけで書き換えない。

### 4. 結果を次へ渡す

条件ごとの判定、対象・証拠、残る制約を整理する。複数単位では単位の結果に加え、統合した成果物を全体の条件で確認する。子の報告や古いCI結果だけで全体を合格にしない。

変更を先へ進める場合は、必須条件の合格を確認し、全体フローで必要とされる [レビュー](review.md)へ渡す。レビュー不要なら直接 [引き渡し](deliver.md)へ進む。検証だけの依頼は、不合格・未確認を含む結果を引き渡しへ渡す。報告の完了と対象の合格・公開可能性を区別し、進行状態と成果判定を別々に記録する。

知識化する価値がある確認済みの結果は、対象の版・証拠・未確認の範囲を添えて引き渡し工程へ渡す。OKFへの保存は引き渡しに任せる。

## 成果物

条件と判定、対象の版・環境、方法・期待値・実測結果・証拠、未確認事項をまとめる。標準以上は通常task.mdへ記し、独立した記録が必要なら同じ場所の `verification.md` に分ける。新規の既定は `.space/tasks/<task-id>/verification.md`。[検証記録のひな形](../assets/verification-template.md)を必要な範囲で使う。

証拠を保存する場合は既存CI等を参照し、独立したファイルが必要なら同じ場所の `evidence/` に置く。小規模は会話、読み取り専用なら記録も回答内にまとめる。未取得の画像・ログ・数値への参照を作らない。

## 終了条件

- 今回確認する条件について、現在の対象と対応する判定・証拠・限界がある。
- 変更を先へ進める範囲では必須条件が合格し、統合が必要な場合は全体も確認している。
- 不合格・未確認がある場合は、影響、戻り先、再開条件が分かる。

検証結果と限界の報告が終了条件なら、その報告を完了にできるが、対象の未確認は残す。必要な検証の実施や条件の充足まで求められている場合は、確認不能の報告だけで依頼を完了にしない。[全体フローの状態と完了の判定](workflow.md#状態と完了の判定)に従う。

## 短縮・再利用・省略の扱い

小規模でも成果物に合う確認は行い、方法と結果を短くまとめる。対象・条件が同じ既存の証拠は再利用できる。変更や新しい懸念がないのに確認を広げたり、同じ検証を繰り返したりしない。

## 失敗時の戻り先

変更まで依頼されている場合は、原因に応じた工程へ指摘と再現・観測結果を渡す。修正後は影響した条件を再確認し、変更前の判定を現在の結果へ流用しない。検証のみなら結果を引き渡す。利用できない手段に依存する場合は、不足と代替手段の限界を示し、独立して確認できる範囲を進める。
