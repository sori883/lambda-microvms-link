# 実装・編集

## 目的

計画で割り当てられた単位を、採用した設計と完了条件に沿って変更する。変更と局所的な確認を小さく往復し、現在の成果物・差分・証拠を検証工程へ渡す。

## 開始時に必要なもの

- 今回の依頼範囲、実装まで進める承認、受け入れ条件。
- 採用または再利用する設計の利用例・骨組み・不変条件。
- 着手する単位、依存する成果物と版、担当・変更範囲、検証方法。
- 現在の作業場所・差分・実行環境、既存の検証結果、記録先と報告先。

小規模で設計・計画を統合している場合は、会話にある変更内容と確認方法を使う。独立した設計書や計画書がないことだけを理由に作業を止めない。

## 手順

### 1. 着手条件と実状態を照合する

[計画](plan.md)の依存が成立し、指定された対象と版に作業できることを確認する。変更前の差分と他担当の所有範囲を把握し、自分が今回加える変更を区別する。分離が必要なら利用先で許可された作業場所を使い、他者の変更を移動・破棄して場所を整えない。

担当範囲や前提が未確定なら計画へ戻す。実装を左右する事実は [調査](investigate.md)、新しい構造や骨組みの矛盾は [設計](design.md)へ戻す。人間の方針が必要な問いは選択肢と影響を示して確認し、その回答に依存しない範囲を進める。

### 2. 一つの結果を具体化する

利用例・型・責務・境界を基準に、現在の実装方式へ合わせて変更する。コードだけでなく、今回の振る舞いに必要な設定・関連文書・生成元も対応させる。生成物がある場合は利用先の生成手順に従い、生成元と配布・実行される内容を区別する。

不具合は確認した原因に対応する変更を行う。短い局所テストで再現できる場合は変更前の失敗を確かめ、修正後に同じ確認を行う。新機能でも有効な振る舞いのテストを使い、実装の文言を写すだけのテストや、低影響の編集に不要なテストを増やさない。局所テストで扱えない再現・実操作の条件は検証へ引き継ぐ。

安価な局所テストの経路がある修正は [tdd](../../tdd/SKILL.md)を使い、Red・Greenの実結果を残す。コメントを整理する場合は [no-comments](../../no-comments/SKILL.md)に従い、価値のある理由・制約をOKFへ保存・照合してから削除する。文章の構成は [technical-writing](../../technical-writing/SKILL.md)、推敲は [unslop](../../unslop/SKILL.md)へ渡す。

判断に根拠がないまま保険的な処理を加えない。仮説が否定された場合は、それを根拠に自分が加えた不要な変更を整理する。改善に見える周辺変更も今回の結果に必要かを確認し、範囲を広げる必要があれば計画を更新する。

骨組みからの変更が必要になったら、理由と影響を示す。境界・不変条件を変える場合や同じ回避策が繰り返される場合は、設計の見直し手順へ戻す。実装の都合だけで採用設計や受け入れ条件を黙って変更しない。

### 3. 差分と局所的な結果を確認する

今回作成・変更・削除したものを、未追跡ファイルを含めて確認する。必要な変更の漏れ、不要な抽象化・重複、一時的な計測用変更の残存、関連する参照の不整合を整理する。既存の他者の変更は保持する。

変更した単位に適切なビルド・テスト・形式確認を行い、期待と実際の結果を記録する。失敗は原因に応じて直し、結果が出ないまま同じ実行を繰り返さない。局所的な成功を、実経路や全体の検証が済んだことにしない。

### 4. 検証へ渡す

単位ID、実現した内容、対象の版と差分、実行した確認と結果・証拠、設計からの変更理由、未確認事項を [検証](verify.md)へ渡す。更新者とタイミングは [全体フロー](workflow.md#進捗の更新者)に従う。子は自分の記録を更新するか親へ報告し、親の受け入れ確認を代行しない。

コミット・PR等の納品操作は今回の依頼範囲で選び、引き渡し工程へ必要な情報を残す。変更ファイルがそろっただけでタスク全体を完了にしない。

知識化に必要な実装範囲、設計との差、未実装の範囲、取得済みの確認結果も引き継ぐ。OKFへ残す候補があれば [引き渡し](deliver.md)へ渡し、保存・更新・検証は原則として引き渡しに任せる。no-commentsで削除前に保存した知識はconceptと照合結果を渡し、重複保存しない。

## 成果物

実装対象のコード・設定・文書等と、変更理由・確認結果・次に確認する範囲を渡す。標準以上は通常task.mdに記録し、独立した経過記録が必要なら同じ場所の `work-log.md` へ分ける。新規の既定は `.space/tasks/<task-id>/work-log.md`。既存の差分・CI・資料への参照を使い、本文やログを重複保存しない。

小規模は会話に結果を残し、task.mdを新規作成しない。実装対象のファイル名は利用先と依頼に従い、成果物としてimplement.mdを一律に作らない。

## 終了条件

- 担当単位の検証に必要な変更がそろい、設計・範囲との対応が説明できる。
- 行った確認と未確認の範囲、対象の版・差分・証拠が分かる。
- 次の検証担当が同じ成果物を確認でき、未完了事項と報告先を引き継いでいる。

変更できない範囲が残れば、完了とはせず不足と再開条件を報告する。

## 短縮・再利用・省略の扱い

既知の局所変更は変更・自己確認・検証を同じ担当で続けて行える。既存の変更を引き継ぐ場合は差分と条件への適合性を確かめ、作り直さない。調査・設計・計画・レビューのみの依頼では実装を追加しない。

## 失敗時の戻り先

原因や前提の不足は調査、構造の問題は設計、依存・所有範囲・単位の問題は計画へ戻す。検証やレビューから戻った場合は、対象の指摘と現在の差分を照合して修正し、影響する確認を再実施する。
