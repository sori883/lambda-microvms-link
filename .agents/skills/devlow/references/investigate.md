# 調査

## 目的

今回の問いに答え、次の設計・計画・変更に必要な事実と制約を明らかにする。確認できたこと、推論、未確認の範囲を分け、根拠とともに次へ渡す。

## 開始時に必要なもの

- 依頼整理で定めた目的・対象・完了条件と、調査で解消する問い。
- 対象のコード・設定・資料、関連する既存設計・OKFの記録。
- 引き継がれた調査結果、検索済みの範囲、再現条件・実行環境の情報。

task.mdがない小規模な依頼では、会話の整理を入力にする。記録の形式をそろえるために依頼整理をやり直さない。

## 手順

### 1. 問いと調べる範囲を絞る

何が分かれば回答できるか、または次の判断へ進めるかを定める。対象ファイル・機能・依存先と、対象の版や環境を確認し、問いに関係する範囲から調べる。周辺の問題は今回の判断に影響するものだけ追う。

### 2. 既存の知識を現状と照合する

引き継いだ資料と検索範囲を先に使う。関連する設計・構成・経緯が不足していれば、既存資料と、利用可能なOKFの記録を検索する。OKFの操作は [全体フローの専門スキルへの接続](workflow.md#4-必要な専門スキルへ渡す)に従い、調査のためにbundleを初期化しない。

資料の対象・版・適用条件をコードや設定と照合する。採用済みの設計と実装済みの構成を区別し、相違は未実装・移行中・文書の古さなどの可能性を根拠から確認する。現在の実装だけを理由に、設計方針を変更しない。

対象コードが分かる場合は、OKFの `code_refs`に対応するパス検索も使い、コード外に残された理由・制約を確認する。再開時の経緯の再構成は [recall](../../recall/SKILL.md)、小さな差分の波及と安全性の前提の確認は [blast-radius](../../blast-radius/SKILL.md)へ範囲を絞って渡す。

既存のブループリントはOKFの記録として参照する。読むためだけにsystem-blueprintを起動しない。

### 3. 必要な根拠を集める

| 問い | 確認すること |
| --- | --- |
| 仕組み・変更の影響 | 入出力、呼び出し元と依存先、設定、境界、既存テストが示す振る舞い |
| 不具合・性能 | 報告された条件、期待する結果と観測結果、再現手順、対象の版・環境、比較に使う基準値 |
| 採用理由・経緯 | 設計判断、変更履歴とその根拠。現在のコードから動機を断定しない |
| 外部仕様・互換性 | 利用中のバージョンと、その版に対応する公式資料等の一次情報 |

狭い問いは直接確認し、構成や経緯を詳しく調べる必要がある場合は全体フローに従ってhow・whyへ渡す。問い、対象、確認済みの知識、未確認事項を引き継ぎ、同じ調査を重複させない。

再現・計測は依頼と権限の範囲で行う。環境への書き込みや外部操作が必要なら、その影響が許可範囲に収まることを確認する。読み取りだけの調査を実行検証と呼ばず、調査中に本体の修正を追加しない。

### 4. 結論と残る問いを整理する

結論を根拠の箇所・対象の版・観測結果と対応付ける。原因候補や設計理由の推論には、その根拠と未確認の条件を添える。情報が矛盾する場合は適用条件や時点を確かめ、解消できなければ両方の根拠と次に必要な確認を残す。

次の工程へ、維持する振る舞い、影響する境界、比較・検証に必要な条件を渡す。新しい設計の採否や実装方法の確定は担当工程で行い、調査結果だけで依頼の目的・範囲を変更しない。

## 成果物

問いと対象、根拠付きの結論、推論と未確認事項、次の判断に必要な制約をまとめる。再現・計測を行った場合は、その手順・条件・期待値・実測結果を添える。取得できなかった資料や結果がなかった検索も、結論の限界に関係する範囲を残す。

標準以上は通常task.mdへ要約と根拠を記す。独立した共有・レビュー・再利用が必要なら、task.mdと同じディレクトリの `investigation.md` に分ける。新規の既定は `.space/tasks/<task-id>/investigation.md`。既存の調査資料を再利用できれば参照し、本文を複製しない。

確定した事実・現在の構成のうち、後のシステム理解に必要な内容を保存候補として識別し、対象・根拠・未確認の範囲を [引き渡し](deliver.md)へ渡す。既存知識の検索・参照は調査で行い、候補の保存は引き渡しに任せる。

現在の構成文書そのものの作成・更新が今回の成果物に含まれる場合は、確認済みの構成・根拠・既存文書・未確認事項を [system-blueprint](../../system-blueprint/SKILL.md)へ渡す。この場合は専門手順内でOKFへ保存できる。返された文書・対象の版・保存と検証の結果を引き渡し工程へ渡し、重複保存を避ける。通常の調査でブループリントの作成を必須にはしない。

小規模は会話にまとめ、task.mdを新規作成しない。調査資料の納品を求められている場合は指定先に保存する。読み取り専用の指定があれば、記録用の書き込みも行わない。途中の調査をそのままOKFへ登録せず、確定した知識の保存は全体フローの引き渡しに従う。進捗の更新者とタイミングも全体フローに従う。

## 終了条件

- 今回の問いへの答えと根拠、対象とした版・条件を説明できる。
- 推論・未確認事項を事実と区別し、次の操作を妨げる不足が解消されている。
- 残る問いの影響と解決先、次の工程が使う資料・再現条件を渡せる。

調査だけの依頼なら、結論と根拠を [検証](verify.md)で確認し、[引き渡し](deliver.md)へ渡す。「確認できなかった」が結論でも、調べた範囲と限界を説明できれば回答できる。後続作業がその不足に依存する場合は、調査回答の終了を着手条件の充足と混同しない。

## 短縮・再利用・省略の扱い

小規模では対象と根拠の確認を回答や実装前の確認へ統合する。既存調査を再利用するときは、今回の対象・版・条件への適合性だけを確認する。親から共通調査が渡されていれば、子は担当範囲の不足だけ調べる。不要な調査の省略は全体フローで選び、未調査を確認済みにしない。

## 失敗時の戻り先

対象・目的・範囲の前提が変わった場合は [依頼整理](intake.md)へ戻す。資料取得・再現・計測ができない場合は、分かった範囲と不足、再開条件を残し、独立して進められる問いを扱う。判断を左右する方針が根拠から決められない場合は人間へ確認し、設計で比較すべき未知はその問いとして渡す。
