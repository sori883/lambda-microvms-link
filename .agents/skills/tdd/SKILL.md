# 失敗を確認してから修正する

期待する振る舞い、観測した不具合、対象の版、最小の再現条件を確認する。製品コードを修正する前に、その不具合を捉える実行可能な確認を用意する。

1. 対象経路に最も近い既存のテストと実行方法を探す。大きな環境構築や壊れやすいモックが必要なら、形式のために新しいテスト基盤を作らない。
2. 利用者が観測する結果を期待値とする、最小の回帰テストを追加する。現在の実装を写して期待値を決めない。
3. 修正前にテストを実行し、意図した不具合で失敗することを確認する。別の原因で失敗した、または成功した場合は再現を見直す。
4. 原因に対応する最小の修正を行い、同じテストを再実行する。
5. 成功後、必要な整理を行った場合は影響する確認を再実行する。周辺の契約や回帰も変更に応じて確認する。

失敗テストが現実的でなければ、対象を動かすスクリプト、再現コマンド、実操作など最も有効な確認を選ぶ。TDDを明示された依頼で代替した場合は理由と違いを示し、失敗前の証拠がないものをRed-Greenの実施済みにしない。

不具合に合わせて期待値を弱めない。仕様変更が正しい場合だけ、その根拠と変更前後を記録する。不安定なテストは再試行で隠さず、条件を固定するか未確認として扱う。

結果には、修正前に失敗した確認と理由、修正後の結果、必要な周辺確認、示せなかった証拠を含める。実装と検証の担当へ同じ対象・版・結果を渡す。
