# 変更の波及を確かめる

対象の差分と基準の版、意図する変化、維持すべき振る舞いを固定する。未コミット変更と生成物も対象に含めたかを示す。結果は影響の一覧と、その判断を支える証拠である。

## 既存の理由・制約を確認する

影響を判断する前に、[OKFスキル](../okf-agent-memory/SKILL.md)で利用先の既存の `.space/babel/`（ユーザー指定があればそのbundle）を検索・参照する。呼び出し元から確認済みの知識と検索範囲が渡されていれば、今回の対象・版への適合性を確かめ、不足分だけ調べる。

対象の実ファイルのパスから `code_refs`に対応する記録を文書種別を絞らず検索し、関連する設計判断・理由も調べる。必要な本文を読み、適用条件・対象の版・根拠を現在のコードと照合する。検索・参照と制約の扱いはOKFスキルの手順に従う。コードだけでは分からない制約を安全性の前提へ含め、古い記録や推測を現在の事実へ置き換えない。

この確認ではbundleの初期化や知識の保存・更新を行わない。bundleなし、関連記録なし、取得不能を区別して報告し、取得できるコード・証拠の調査を続ける。未取得を理由に制約なし・影響なしと判断しない。

## 影響経路と前提を調べる

1. 変更した入出力・状態・公開契約から、呼び出し元、依存先、後続の処理を追う。既存の構成を理解する必要があれば [how](../how/SKILL.md)、設計理由が必要なら [why](../why/SKILL.md)へ具体的な問いと確認済みの情報を渡す。
2. シンボル検索に現れない接続を確かめる。保存形式、APIの応答、別言語の利用側、設定・フラグ、非同期処理と終了処理、配布・起動時の境界が該当する。依存ライブラリは使用中の版とパッチを確認する。
3. 「この前提が成り立つから影響を限定できる」という判断を特定する。一つに絞れない場合は独立した前提に分ける。架空の利用側や可能性だけでリスクを増やさない。
4. 前提ごとに、発生条件、到達する経路、影響をコードの位置と結び付ける。確認した危険、調べて除外した危険、未確認を分ける。確率の根拠がなければ数値を付けない。

## 前提を実行で確認する

許可された環境で、実際の実装と依存を通る最小のテスト・スクリプト・操作を選ぶ。誤った前提なら失敗すると分かる入力と期待値を使い、対象の版、手順、結果、証拠を残す。既存の適合する検証は再利用する。

読み取り専用なら実行やファイル作成へ広げず、到達経路と既存証拠を調べる。各前提について、ソース照合まで、経路上の反証まで、実装の実行まで、実環境の再現までのどこを確認できたかを示す。実行不能・曖昧な結果を合格にしない。

調査のために製品コードを修正しない。広い変更を分担する場合は影響経路を分け、同じ版・前提・出力形式を渡す。複数の担当が同意したことを実行証拠の代わりにしない。

## 結果を渡す

- 実際に変わる振る舞いと、影響する利用側・境界。
- 安全性を左右する前提、確認の到達点、根拠と実行結果。
- 確認したリスク、除外したリスク、未確認の範囲。
- 確認したOKFのbundle・concept ID・根拠箇所、検索範囲と取得できなかった情報。
- 残るリスクを判定するための最小の検証と、変更を進める条件。

既存タスクの調査・検証記録へ結果を返す。説明だけの依頼では回答内に留める。実行結果から設計・計画の見直しが必要なら、その理由と対象を担当へ返す。
