# 採用理由を調べる

コードの背景にある動機と意図を調べる。

`how` と対になるスキル。`how` はコードが何を行い、どう動くかに答える。`why` は、どのような事情がその形をもたらしたかに答える。

## 実行環境への対応

利用環境が提供するサブエージェント機能で、以下の調査担当・統合担当を起動する。役割に対応する設定があれば使い、なければ汎用のサブエージェントへ担当プロンプトを渡す。モデルは利用環境の設定または親からの継承に従い、特定のモデルIDを指定しない。

全担当はコード・履歴・PR・リポジトリ内の資料・OKFの既存記録の読み取りと検索だけを行い、ファイルや外部状態を変更しない。読み取りに必要なツールを使える構成にし、既存の権限制限を尊重する。サブエージェントや必要なツールを利用できない場合は制約を報告し、実行していない調査を実行済みと扱わない。

## 調査の姿勢

**慎重で注意深く、正確な調査担当**として行動する。分かっていることと推論していることを正直に区別する。[根拠と確度の指針](references/epistemics.md)を読み、確度の区分と表現を確認する。統合担当も必ず従う。

## 1. 対象と質問を理解する

**対象**はコードの一部、パターン、機能、名前のある設計判断など。**質問**は設計理由、トレードオフ、動機となった境界条件、外部制約、使われなくなったコード、広い範囲の経緯などである。

対象が曖昧なら、開いているファイル、直近の編集、カーソル位置、会話の内容から解釈する。解釈を短く示してから進め、ユーザーが修正できるようにする。

## 2. 調査の起点となるコードを特定する

調査担当を起動する前に、具体的なコードを起点にする。次をその場で集める。

- 関連ファイルのパスと行範囲。
- 主要なシンボル。関数名、クラス名、定数。
- 対象に触れた直近のコミット一覧。
- マージコミットの題名にある `(#1234)` 形式のPR番号。

```bash
# 対象行を最後に変更したコミット
git blame -L <start>,<end> <file>

# 改名を追跡した、差分付きのファイル履歴
git log --follow -p -- <file>

# ファイルに触れた直近のコミット。PR番号も確認する
git log --oneline -20 -- <file>

# コミットメッセージからPR番号を確認する
git log -1 --format=%B <commit>
```

実質的な変更を含むコミットについて、PRを特定でき、`gh` が利用できる場合はPR本文と議論を取得する。

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

ファイルパス、シンボル、コミット、PR番号、関連チケットIDを、調査の起点となる情報として各担当へ渡す。

Git履歴がない、`gh` が未導入・未認証、PRが取得できないなどの制約は記録する。利用できる根拠の調査を続け、取得できなかった情報を推測で補わない。

## 3. 調査担当を起動する

調査担当を起動する前に、[OKFスキル](../okf-agent-memory/SKILL.md)で利用先の既存の `.space/babel/`（ユーザー指定があればそのbundle）にある関連する決定・制約・経緯を確認し、採用理由の根拠として評価する。[OKFの記録を調べる観点](references/sources/okf.md)に従い、検索・参照だけを行う。呼び出し元から確認済みの記録と検索範囲が渡されている場合は、それを引き継ぎ、不足分だけ調べる。

調査対象はGit履歴、PR本文・レビュー、コードコメント、テスト、リポジトリ内のADR・設計資料・リリースノート、OKFの既存記録とする。[調査手順の一覧](references/source-playbook.md)に従って、質問に関係する記録を調べる。

対象ファイルが分かる場合は、OKFのパス検索で `code_refs`に対応する理由・制約も確認する。コードコメントから移された記録は、本文にある元の位置・版・出典と照合し、保存した時点と元の判断時点を混同しない。

既定では調査担当（why-investigators）を1人起動する。複数の独立した設計判断・コード範囲・変更時期を調べる場合は、重複しない担当範囲を決めて並行して起動してよい。各担当には、担当範囲の読み取り・検索に必要なツールを使えるようにする。

各担当に渡すもの：

1. [調査担当へのプロンプト](references/investigator-prompt.md)。
2. [コードの履歴調査](references/sources/code-archaeology.md)・[OKFの記録を調べる観点](references/sources/okf.md)と、担当する対象・期間・問い。
3. 対象が防御的な処理（nullチェック、再試行、タイムアウト、レート制限、機能フラグ、外向き通信のガード、メモリー不足への対処）なら、[障害と振り返りの観点](references/sources/incident-postmortem.md)。
4. 手順2のコードの情報。ファイルパス、シンボル、コミットハッシュ、PR番号、チケットID。
5. `{EXISTING_KNOWLEDGE}` に入れる既存知識。対象bundle、確認したconcept IDと根拠箇所、検索範囲、未確認事項。取得していない場合はその理由。
6. ユーザーの元の質問。

### OKF参照の受け渡し

調査担当・統合担当を起動するときは、OKF参照を**参照元ファイルが実際に配置されているディレクトリ**を基準に解決し、次を担当プロンプトへ入れる。

- `{OKF_SOURCE_PATH}`：担当プロンプト内の `sources/okf.md` への相対リンクから解決した、同資料の絶対パス。
- `{OKF_SKILL_PATH}`：上で特定した `okf.md` 内のOKFスキルへの相対リンクから解決した、OKFの `SKILL.md` の絶対パス。

解決先を読み取れることを確認する。担当プロンプトや `okf.md` を本文だけで渡す場合も、解決したパスを一緒に渡す。絶対パスは起動時に求める。利用先プロジェクトの作業ディレクトリは変更しない。解決・読み取りができない欄には「利用不可」と理由を記し、OKFを未確認として扱う。

### 調査範囲と不足を記録する

検索した資料、検索語、対象期間、見つからなかったこと、取得できなかった資料と理由を記録する。調査対象外のサービスへのリンクやチケットIDは手がかりとして残し、自動的に別サービスの調査へ広げない。

単一コミットの小さな対象で、PR本文に完全な答えがあり、関連する履歴・資料を確認して追加調査が冗長だと判断できた場合は、その場で回答してよい。その判断の根拠と調査範囲を示し、確度と出典を含む出力形式は維持する。

## 4. 統合する

統合担当（why-synthesizer）を1人起動する。出典の抜き取り確認に必要なコード・履歴・PR・リポジトリ内の資料を読み取れるようにし、OKFの記録の確認にはOKFスキルを使えるようにする。統合担当も書き込みは行わない。

渡すもの：

1. 全調査担当の結果と、起動前に確認したOKFの既存記録。結果ゼロ、未調査・取得不能の範囲とその理由も含める。
2. コードの情報。ファイルパス、シンボル、コミットハッシュ、PR番号、チケットID。
3. ユーザーの元の質問。
4. [根拠と確度の指針](references/epistemics.md)。
5. [統合担当へのプロンプト](references/synthesizer-prompt.md)。
6. 手順3の「OKF参照の受け渡し」で解決した `{OKF_SOURCE_PATH}` と `{OKF_SKILL_PATH}`。

## 5. 提示する

統合担当の出力をユーザーへ提示する。分かりやすさや会話の文脈に合わせた軽い編集はよいが、**確度を表す言葉を書き換えない。**

## 出力形式

[統合担当へのプロンプト](references/synthesizer-prompt.md)の「質問」「対象コード」「確認できたこと」「合理的に推論できること」「競合する仮説」「分からなかったこと」「調べた情報源」「確度の要約」を使う。必要に応じて調整しても、確度の区別は維持する。「調べた情報源」には担当ごとに1項目を置き、結果ゼロや省略も理由とともに含める。

質問が実際のコード変更に向けた調査であれば、「調べた情報源」の後に、経緯から得た条件を「維持すること・変更すること・避けること・リスク」に整理し、変更計画へ渡せる形にする。

## 避けるべき失敗

- **新しい記録への偏り。** 最後のコミットだけを正本と扱わない。現在の形は過去の複数の判断が積み重なった結果かもしれない。さかのぼって調べる。
