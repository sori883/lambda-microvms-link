# 根拠と確度の扱い

過去の証拠が断片的で、時には矛盾する状況で、確度を判断し、不確実性を消さずに伝えるための指針。

コード自体は採用理由を語らない。何をするコードかは読めても、なぜ存在するかは読み取れない。その理由はコミット、PR本文・レビュー、コードコメント、設計資料に残るが、どれも不完全で偏りがあり、まったく残っていないこともある。そうした限界を無視すると、確信に満ちた推測でユーザーを誤らせる。

## 確度の区分

最終出力のすべての主張を、次のいずれかに分類する。区分に応じて、記載する節と表現を決める。

### 1. 直接の根拠あり（Direct）

質問に答える理由が文章で明記されている。「コードがXを行うから、作者はXを意図したはず」という推測ではなく、作者が実際に書いた理由がある。

例：

- 「項目数が1,000を超えるユーザーがページ送りできない不具合を修正する」と書かれたPRの説明。
- 「顧客Acmeのセキュリティレビューで求められたため追加する」と書かれたPR本文。
- 「上流APIが大きな値を拒否するため100に制限する」というコードコメント。
- 「再起動を越えて永続化する必要があるため、案Bではなく案Aを選ぶ」という設計文書。
- 「従来の方法ではテストが不安定だったため切り替える」という作者のレビューコメント。

表現は明確に、現在形で書く。「Xのために存在する」と述べ、出典を示す。

### 2. 複数の裏付けあり（Supported）

複数の間接的な証拠が同じ説明を支持する。単一の資料に明記されてはいないが、資料を合わせると可能性が高い。

例：

- PRの題名が「性能改善」、リリースノートに処理時間の短縮が記載され、周辺のコミットも同じ実行頻度の高い処理を変更している。
- 変更と同時に追加された複数のテストが、いずれも非常に大きな入力の境界条件を扱っている。
- 同じ作者が同じ週に作成した複数のPRで、同じ障害に言及している。

表現は強い裏付けを伝えつつ、証拠から導いた判断だと明示する。「次の証拠はXを強く支持する」と具体的に示し、複数の出典を付ける。

### 3. 推論（Inferred）

状況から合理的に解釈できるが、それを明示的に裏付ける記録はない。記録上の事実ではなく、あなたの解釈だと読者に伝える。

例：

- PRに理由はないが、リポジトリ内の障害記録の時刻と修正のマージ時刻が近いため、緊急修正だった可能性がある。
- 関数名が再試行を示し、回数は3回で、ほかのコードにあるチームの慣例とも一致する。

「〜と見られる」「可能性が高い」「〜を示唆する」「〜と整合する」「一つの解釈は」と書く。「AとBから、Dという理由でCの可能性が高い」のように推論の過程を示す。

### 4. 仮説（Speculative）

もっともらしい仮説だが、根拠が薄く、別の説明も同程度に成立する。示す価値はあるが、推測だと明示する。

例：

- 「既に修正されたブラウザーの不具合への回避策かもしれないが、当時の根拠は見つからなかった」。
- 「SLAに合わせた閾値の可能性はあるが、この値に言及するSLA文書はない」。

「Xの可能性はあるが、直接の根拠はない」と書く。通常は「競合する仮説」の節に、ほかの可能性と並べる。

### 5. 不明（Unknown）

調べたが分からなかった。有効で重要な結果として記録する。

「X・Y・Zを調べたが、理由を示す根拠は見つからなかった」と、調査対象を具体的に書く。単に「分からなかった」とせず、検索語、対象期間、読んだPR、閾値を検索した範囲などを示す。

## 表現の指針

### 確度の高さを示す言葉

次の表現はDirectまたはSupported相当の確度を示す。推論には使わない。

- 「〜だから」：根拠のある因果関係を表す。
- 「理由は〜」：同じく因果関係を表す。
- 「〜するために設計された」：作者の意図を断定する。
- 「修正する」「対処する」「解決する」：変更が目的を達成したと述べる。
- 「チームが決定した」：集団としての決定があったと述べる。

これらを使う場合は、直近に出典を置く。

### 推論に使う言葉

- 「〜と見られる」
- 「〜のようである」
- 「可能性が高い」
- 「〜を示唆する」
- 「〜と整合する」
- 「一つの解釈は〜」
- 「〜と考えられる」
- 「〜だった可能性がある」
- 「根拠は〜を支持する方向にある」

これらは、記録の報告ではなく解釈だと伝える。「合理的に推論できること」の節で使う。

### 避ける言葉

- 「当然」「明らかに」「もちろん」：本当に自明なら、ユーザーは尋ねていない。
- 「単に性能のため」などの「単に」：不確実性を隠し、問いを軽く扱いがちである。
- 「私は思う」「私は信じる」：個人的な意見ではなく根拠を統合しているため、「根拠からは〜が示唆される」と書く。

### 後付けの正当化を避ける

現在は合理的に見えるコードでも、当時の理由が既に失効していたり、当初から誤っていたりする。複雑な経緯に、整った理由を後付けしない。

- 作者が正しい判断をしたはずだと仮定し、逆算して正当化しない。
- 一貫したパターンがあっても、意図的だったと決めつけない。コピーの結果かもしれない。
- 証拠がないことを、不在の証拠にしない。「セキュリティへの言及がないから、懸念されていなかった」とは言えない。

## ユーザーの仮説を追認しない

「性能のためだと思うが、なぜこうしているのか」のように、質問に仮説が含まれる場合がある。そのまま肯定せず、候補の一つとして独立に根拠を調べる。支持する証拠があれば出典付きで示し、なければその旨と、実際の証拠が支持する内容を伝える。

ユーザーの推測は調査のきっかけであり、正当化すべき結論ではない。

## 根拠が矛盾する場合

PRと設計資料で説明が異なる場合などは、両方を示す。話を整えやすいほうだけを選ばない。

- **設計資料**：「顧客Xのコンプライアンス要件に必要」。
- **PR**：「この領域の技術的負債を整理する」。

両方が正しい可能性も、一方が誤っている可能性もある。出典とともに示し、ユーザーが判断できるようにする。

## 根拠が見つからない場合

正直な「分からない」は、このスキルの重要な成果である。ユーザーは、通常探す場所には答えがないこと、原作者・プロダクト責任者・チームリーダーへの確認が必要なこと、あるいはこれ以上調べない選択肢があることを理解できる。

不足を隠し、確信のある推測で埋めると、ユーザーがその推測に基づいて行動してしまう。不足は具体的に記す。

- 答えようとした質問。
- 調べた情報源。
- 各情報源で検索した内容。
- 得られたもの。何もない場合や、周辺情報だけの場合も含む。

## 最終確認

統合担当は「確認できたこと」と「合理的に推論できること」の各主張について確認する。

1. 出典はあるか。なければ追加するか、推論・仮説に分類し直す。
2. 区分に見合う表現か。Directは「〜だから」と言えるが、Inferredでは断定しない。
3. コードの動作自体を、その採用意図の証拠にしていないか。該当すれば削除または再分類する。
4. 「分からなかったこと」の節があるか。不足が一切ないなら、例外的に根拠が揃っているのか、何かを隠していないか確認する。
