# ブループリントの文書モデル

## 保存先とconcept

利用先の `.space/babel/` を一つのOKF bundleとして使う。新規文書の標準保存先は、構成・動作の説明が `knowledge/systems/<system>/`、根拠のある設計判断が `decisions/systems/<system>/`。いずれもbundle内の相対パスである。

`<system>` には、対象システムを表すファイルパス用の識別名を入れる。単一システムでも省略せず、同じ対象ではknowledgeとdecisionで同じ識別名を使う。次の基準で決める。

- 既存のシステム識別名があれば、それを使う。
- なければ、対象システムを表す名前を英小文字・ハイフン区切りで決める。例：`order-management`。
- 新しく決める際、リポジトリ全体が一つのシステムなら、リポジトリ名を候補にする。複数の独立したシステムがある場合は、対象システムごとに識別名を決める。

一度決めた識別名は、以後の更新でも使い続ける。文書のタイトルには日本語のシステム名を使ってよい。例えば、識別名を `order-management`、タイトルを「受注管理システムのブループリント」とする。

新規作成には次のconcept IDを使う。詳細文書は独立して参照・更新する意味があるものだけを作成し、空の文書やディレクトリを先に作らない。

| 新規作成時のconcept ID | type | 扱う内容 |
| --- | --- | --- |
| `knowledge/systems/<system>/blueprint` | `knowledge` | 目的・範囲・全体構成と、詳細conceptへの案内 |
| `knowledge/systems/<system>/components/<component>` | `knowledge` | 独立した構成要素の責務・境界・入出力・依存 |
| `knowledge/systems/<system>/flows/<flow>` | `knowledge` | 代表的な操作に対する、構成要素をまたぐ処理とデータの流れ |
| `knowledge/systems/<system>/deployment` | `knowledge` | 実行単位・起動・配置・環境差 |
| `decisions/systems/<system>/<decision>` | `decision` | 確認できた一つの判断と、その理由・制約・影響 |

実ファイルはbundle内のconcept IDに `.md` を付けた場所へ保存される。例えば、全体像は `.space/babel/knowledge/systems/<system>/blueprint.md` となる。`blueprint` は目次の代用ではなく、全体を理解するための説明を持つknowledgeである。

既存conceptの検索結果を優先し、同じ対象・責務の文書が別の場所にあっても、そのIDを使って更新・参照する。標準配置に合わせるためだけの移動・複製は行わない。

## OKFスキルによる保存

[OKFスキル](../../okf-agent-memory/SKILL.md)の手順に従い、OKF CLIを使って、上表のconcept IDとtypeでファイルを作成する。既存文書は検索で確認したIDで更新する。対象bundleは利用先の `.space/babel/` とし、標準配置のサブディレクトリを別のbundleにしない。

CLIの準備、コマンド書式・引数、作成・更新・関連付け・形式検証の実行方法は、OKFスキルを正本とする。この文書ではブループリント固有の保存先・concept ID・typeを定義する。

## 分割の判断

システムの規模ではなく、別々に検索・参照・更新する価値があるかで分ける。

- 全体像と、独立した責務を持つ構成要素の詳細を分ける。ソースファイルやクラスを機械的に1文書ずつ写さない。
- 複数の構成要素をまたぎ、順序・分岐・データ変換の説明が必要な経路はflowにする。単純な内部処理はcomponentに含める。
- プロセス・ホスト・環境差が、論理構成とは別に理解・更新されるならdeploymentにする。配置が未確認なら不明と記す。空欄を埋めるために想像のクラウド構成を作らない。
- 一つの決定の理由・代替案・影響を別々の文書にしない。判断を確認できる資料があるときはdecisionを作成または更新する。採用理由が不明ならその旨を残す。whyの仮説だけから、合意済みの決定を作らない。
- 未解明事項は、それが属するconceptに記す。全体の理解に影響するものはblueprintから案内する。未解明という状態だけを基準に、無関係な問いを一つの正本文書へ集めない。
- 空の文書や、ほかの文書の言い換えにしかならない文書は作らない。全体像だけで内容が完結し、独立した詳細が存在しない対象は、分割のためだけに断片化しない。

## 文書ごとの内容

必要な情報を、対象に合わせて短く書く。該当しない節は省けるが、必要なのに確認できない項目は不明として明示する。

### 全体像

- システムの目的、利用者、対象範囲、範囲外。
- 全体構成図。主要な要素、外部との境界、関係の意味。
- 構成要素の短い説明と、対応する詳細conceptへのリンク。
- 代表的なフロー、配置、重要な判断への案内。
- 調査の基準時点と範囲、全体に影響する未解明事項。

### 構成要素

- 責務と境界。担当することと、ほかの要素が担当すること。
- 入口・公開インターフェース、入出力、依存先。
- 所有する状態やデータ、主要な内部構造、必要な失敗時の動作。
- 対応するコード、関連するフロー・決定へのリンク。
- 根拠、未解明事項。

### 処理フロー

- 起点となる操作、前提、結果。
- 関係する構成要素、処理順序、受け渡すデータ、重要な分岐。
- 同期・非同期、状態の更新、失敗・再試行など、理解に必要な動作。
- Mermaidのシーケンス図やフローチャートと、対応するコードの根拠。
- 関連concept、未解明事項。

### 実行・配置

- 実行単位、起動方法、重要な初期化順序。
- 配置単位、接続先、実行に影響する設定の名前と役割。秘密値を転記しない。
- 確認できた環境差と、対象にした設定。
- 設定から読んだ構成と、実環境を観測した事実の区別。
- 根拠、関連concept、未解明事項。

### 決定

- 何を、いつの記録で決めたか。日付や主体が不明なら捏造しない。
- 背景の問題・制約、選んだ方法、採用理由。
- 記録で確認できる場合は、検討した代替案と選ばなかった理由。
- 結果として生じる利点・代償・制約。観測、記録された予測、推論を区別する。
- 出典とwhyの確度、現在の構成との対応、後継の決定があればリンク。

過去の理由を、現在も有効な制約として自動的に強制しない。判断の当時の背景と、現在確認できる状態を分ける。

## 根拠と未解明事項

文書単位の `sources` に出典を記録し、本文では重要な主張の近くに、該当するファイル・シンボル・資料の節・PRなどを示す。資料を一覧に載せただけで、すべての主張が裏付けられたことにはしない。

whyから受け取ったDirect・Supported・Inferred・Speculative・Unknownの区分を保持する。特にSupportedを「作者がそう決めた」というDirectの記録に書き換えない。重要な判断には、元の確度を日本語の説明とともに残す。

| 状態 | 残す情報 |
| --- | --- |
| 未調査 | 今回調べていない範囲と理由 |
| 調査したが不明 | 問い、調べた資料や期間・検索語、得られた範囲 |
| アクセス不能 | 利用できない情報源と理由 |
| 矛盾あり | 食い違う記述と両方の出典、確認できた実装の状態 |

推論や仮説を残す場合は、根拠と不確実性を同じ場所に書く。欠けている根拠のために文書全体を未完成扱いせず、説明できる範囲と限界を明確にする。ユーザーの意図が必要な問いは確認事項として示し、勝手に関係者へメッセージを送らない。

## 更新と関連付け

同じ対象・責務は同じIDで更新する。既存conceptを読み直し、新しい証拠に関係する箇所だけを改め、無関係な知識やメタデータを消さない。以前の根拠が否定されたのか、別条件の説明なのか、単に未確認なのかを区別する。

blueprintから詳細へ「構成要素の責務」「注文受付から保存までの流れ」など意味のある説明を付けて関連付ける。詳細から必要な決定や構成要素へつなぐ。同じ内容を双方へ複製したり、検証の孤立判定を消すためだけに無関係な文書をつないだりしない。

更新で不要になった文書は、利用先の既存の扱いとユーザーの範囲指定に従う。自動的な物理削除や、単なる追記による矛盾の温存を避ける。
