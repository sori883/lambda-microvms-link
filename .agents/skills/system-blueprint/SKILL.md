# システムのブループリントを作成する

既存のコードや資料から、対象システムの構成・動作・設計背景を理解できるブループリントを作成・更新する。ブループリントは文書群全体を指し、`blueprint.md` は全体像と詳細への入口を担う。

現在の構成を根拠付きで説明する。改善案や将来構成の設計を、既存構成の説明に混ぜない。理由が不明でも、確認できた構成・動作と不明点を区別して文書を完成させる。

## 利用するスキル

このスキルと次の3スキルを一緒に配布する。相対リンクは同じ親ディレクトリに配置した構成を想定する。

| スキル | ブループリント作成での役割 |
| --- | --- |
| [how](../how/SKILL.md) | 実装から構成・責務・境界・処理とデータの流れを調べ、根拠付きで説明する |
| [why](../why/SKILL.md) | 重要な構成判断の理由を調べ、確認できた根拠・推論・仮説・不明を区別する |
| [okf-agent-memory](../okf-agent-memory/SKILL.md) | 既存conceptの検索、文書の作成・更新・関連付け、目次・履歴の同期、形式検証を行う |

必要な段階で各スキルを読み、その手順を使う。how・whyの調査手順をここへ複製しない。調査担当には結果を返してもらい、ブループリントを作成する担当が文書群を統合してOKFに保存する。

## 1. 対象と既存のブループリントを確認する

ユーザーの対象指定、用途、読者、今回説明する境界を確認する。既存システム全体の依頼なら、リポジトリや設定からシステム境界を見つけ、解釈を短く示して進める。複数の独立システムがあり対象を決められない場合は確認する。

保存先のOKF bundleは**利用先プロジェクトの `.space/babel/`**。新規文書は、構成・動作の説明を `.space/babel/knowledge/systems/<system>/`、根拠のある設計判断を `.space/babel/decisions/systems/<system>/` に作成する。全体像の入口は `knowledge/systems/<system>/blueprint.md` とする。単一システムでも、対象の安定した識別名である `<system>` を省略しない。詳細の標準配置は[文書モデル](references/document-model.md)に従う。

このスキルを開発・配布するリポジトリや、スキルのインストール先に、利用先のブループリントを生成しない。ユーザーが別のbundleを明示した場合は、そのbundle内で同じ標準配置を使う。

OKFの手順で対象システムに関する既存のknowledge・decisionを検索し、候補のdescriptionから読むconceptを選ぶ。同じ対象と責務の文書があれば更新し、既存ID・リンク・独自メタデータを保持する。bundleがなければOKF CLIで初期化する。

確認した既存文書、README、仕様、マニフェスト、起動設定から調査の入口を作る。既存文書の説明は実装と照合するための材料であり、現在の動作を保証するものとは扱わない。

## 2. howで構成と動作を明らかにする

howには、対象システム、境界、読者、既に確認した情報、調べたい構成・経路を渡す。ソースコード、設定、既存文書、関連するテストから実装を追ってもらう。調査対象は、次のうちシステムの理解に必要なもの。

- 利用者、外部システム、アプリ・サービス・データストアの境界。
- 主要な構成要素の責務、インターフェース、依存の方向、実際に使う技術。
- 代表的な操作・API・コマンド・ジョブの入口から、処理とデータの行き先まで。
- 永続データの所有者、同期・非同期の連携、重要な失敗・再試行の動作。
- 起動・初期化、実行プロセス、配置単位、外部連携、環境による差。

ディレクトリ名や依存パッケージの存在だけから、設計方式や実際の利用を断定しない。モノレポのパッケージ境界と実行単位、開発用設定と本番用設定を区別する。生成物を元の実装として読まない。

howの説明と参照箇所から、構成要素・関係・フロー・未解明事項を整理する。矛盾や追跡できない接続があれば、該当するコードや設定に戻って確かめる。配置設定から確認できるのは設定上の構成であり、実環境を確認していなければ「本番で稼働中」とは書かない。

## 3. whyで重要な設計判断の背景を確認する

システム境界、データの所有、通信方式、依存技術、重要な品質特性に関わる判断について、既存の決定記録や設計資料を確認する。既に根拠と理由が十分にある判断は、それを使う。

理由の不足が構成の理解や変更判断に影響する場合は、whyに**具体的な問い**を渡す。対象コードのパス・シンボル、関連するコミット・PR・既存decision、今回知りたい理由を添える。howで未追跡の実装を調べることと、whyで採用理由を調べることを区別する。

whyを使う場合は、配布しているwhyの調査範囲と手順に従う。調査した範囲と取得できなかった根拠を記録する。既知の根拠と同じ問いを繰り返し調べず、追加調査は新しい手がかりや結論を左右する矛盾がある場合に行う。

whyの区分と確度を保持する。複数の裏付けからの判断を、当時の明示的な決定に置き換えない。出力には「未調査」「調査したが根拠なし」「情報源にアクセスできない」「資料が矛盾」を区別して残す。理由が分からないことだけを理由に、文書作成を止めない。

## 4. ブループリントを文書群として構成する

[文書モデル](references/document-model.md)を読み、対象と責務、独立して参照・更新する単位に合わせてconceptを分ける。大小ではなく意味の単位で判断する。固定数の文書を作るために、空の文書や細かすぎる断片を増やさない。

[ブループリントの本文ひな形](assets/blueprint-template.md)を全体像の出発点とする。詳細は文書モデルに沿って作り、全体像から関連付ける。全体像に詳細文書の本文を複製せず、要約と「何を知りたいときに読むか」を示す。

図はMermaidで作り、構成要素、境界、矢印の意味が本文と一致するようにする。全体構成と具体的な処理フローの図を、必要な粒度で分ける。図の各関係に根拠を対応させ、不明な接続を確定した関係として描かない。

各文書で、対象と調査範囲、調査日、参照リビジョン、根拠、不明点を追跡できるようにする。未コミット変更を読んだ場合はその旨を記す。Gitを使わない場合や履歴を取得できない場合は、架空のコミットを記録しない。

## 5. OKFへ保存し、内容と形式を検証する

文書の作成・更新・関連付け・形式検証は、[OKFスキル](../okf-agent-memory/SKILL.md)の手順に従い、**OKF CLIを使う**。新規文書は、文書モデルで定義したconcept IDとtypeで標準配置に保存する。既存文書は検索で確認したIDで更新し、標準配置に合わせるためだけに移動・複製しない。CLIの準備や実行方法はOKFスキルを参照する。

構成・動作の説明は `knowledge`、根拠のある決定とその背景は `decision` とする。説明を強制ルールにしないため、原則として `governance: context` を使う。現行の制約として別途合意されたものは、既存の扱いを確認する。

根拠を `sources`、関係する利用先のコード範囲を `code_refs` に記録する。`generated` はCLIが実際の主体と日時から記録する。人間の内容確認を受けていなければ `verified` を追加しない。本文の相対リンクは文書の位置、`code_refs` は利用先プロジェクトのルートが基準である。

保存後はOKFスキルの手順で文書を読み返し、次を確認する。

- 全体像から主要な詳細をたどれ、同じ事実の正本が重複していない。
- 構成要素の責務、接続の向き、処理フロー、配置がコード・設定・資料の根拠と一致する。
- 理由と観測した動作を混同せず、推論・未確認・矛盾が本文と図で失われていない。
- 既存の文書や根拠へのリンクが正しく、保存したdescriptionから必要なconceptを検索できる。

形式検証はOKFスキルの手順に従い、内容の照合とは別々に結果を示す。既存bundleの無関係な問題を解消するためだけに文書を変更せず、既存の問題と今回の変更による問題を区別する。保存や検証の失敗を成功扱いせず、実際に保存できた範囲と残件を報告する。

## 6. ブループリントを案内する

全体像のconcept、作成・更新した詳細、今回説明できる範囲、重要な未解明事項、内容確認と形式検証の結果を短く伝える。完了条件は「すべての理由を解明した」ことではなく、対象範囲について確認できた構成・動作・設計背景と、推論・不明点が根拠付きで区別され、文書群として保存・検証されていることである。
