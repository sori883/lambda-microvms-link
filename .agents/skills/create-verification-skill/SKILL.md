# プロジェクト専用の検証スキルを作る

次の担当が会話を知らなくても動かせる検証手順を、利用先プロジェクトに作る。既存の検証スキルがあれば拡張し、同じアプリ向けの正本を増やさない。

## 実際の起動と操作を調べる

コード・README・設定・既存テストから次を確認する。分かることを利用者へ聞き直さない。

- 利用者の入口。UI、CLI、API、ライブラリなど、複数ある場合はそれぞれ識別する。
- 起動・終了コマンド、準備するデータ、環境変数、認証、使用するポート。
- 既存の操作手段。ブラウザテスト、PTY、HTTP、公開APIなどを優先して使う。
- 観測できる出力と副作用。画面、終了コード、ファイル、データ更新、ログなど。
- 同時実行の条件。ポート、プロファイル、データを分離できるか、共有環境なら誰が操作するか。

起動不能なら原因を示す。修復が依頼範囲に含まれない場合は製品を修正せず、未実行の草案として扱う。秘密値はスキルへ埋め込まず、取得方法と必要な変数名だけ記す。

## 利用先に生成する

既存のスキル配置と実行製品を確認し、その製品が読み込むプロジェクト用スキルディレクトリに `verify-<app>/` を作る。配置先が不明なら現行の製品仕様を確認する。プラグインのインストール先や配布元に生成しない。複数製品で使う場合は利用先の共通管理方法に合わせ、同期されないコピーを増やさない。

`SKILL.md` のfrontmatterには `name` と、対象アプリ・検証の起動条件が分かる `description` を書く。本文には次を具体的なコマンドと実在する対象で記す。

| 項目 | 必要な内容 |
| --- | --- |
| 起動 | 準備・起動・準備完了の判定。短命のCLIは操作ごとに分離した実行を行う |
| 状態確認 | 正しい版・プロセス・認証・データを操作しているか調べる読み取り専用の確認 |
| 操作 | 利用者が通る入口と、安定した識別子・コマンド・入力 |
| 証拠 | 入力と結果、副作用、対象の版と環境、保存先。テスト用内部操作だけで利用経路の証明にしない |
| 後片付け | この実行が開始したプロセスと一時データだけを片付ける。証拠は残す |

外部送信・購入・データ削除などを操作する場合は、その実行に必要な依頼範囲と権限を明記する。dry-runという名前だけで無変更と扱わず、実際のファイル・通信等への影響を確かめる。再利用する補助スクリプトを同梱するなら、依存、実行方法、失敗時の終了を明示する。

## 機能ごとの確認手順を作る

`features/README.md` を機能一覧とし、主要な利用機能から機能別のファイルを作る。[機能資料のひな形](assets/feature-template.md)を利用先の実情報で埋める。機能の入口、前提、操作、期待する最終状態と証拠を対応付ける。未確認の機能は未確認と記し、網羅したことにしない。

## 生成した手順を実行する

生成した説明に従って、起動、状態確認、少なくとも一つの機能の操作、証拠保存、後片付けまで通す。失敗した試行も自分が開始したものを片付け、証拠が残ることを確認する。手順や補助スクリプトを修正したら、影響する操作を再実行する。

保存先、確認した版、実行した機能、未確認の機能、証拠、残る前提を報告する。全機能を動かしていない場合は全体を検証済みにしない。未実行なら草案として渡す。実装変更後の手順更新には [maintain-verification-skill](../maintain-verification-skill/SKILL.md)を使う。
