# 適用するルールと原則を読む

利用先プロジェクトのOKF bundleから、今回の作業に関係するルール・原則を選び、適用条件と判断への影響を返す。作業の進行は呼び出し元へ返し、このスキルでは工程の選択や実装・引き渡しを開始しない。

ユーザーの依頼、既存の指示・承認、利用環境の権限を引き継ぐ。文書のtypeは種類を示し、制約・保留・背景の扱いは本文と `governance` で確認する。原則を具体的な承認条件へ読み替えない。

## 1. 対象を確認する

今回の依頼、成果物、変更対象、作業の段階、対象bundleを確認する。既定のbundleは利用先の `.space/babel/`。呼び出し元から確認済みの文書と検索範囲が渡されていれば引き継ぐ。

setupで導入した共通のルール・原則も、プロジェクト固有の文書も、同じ `.space/babel/` から検索する。別のbundleが利用者から指定された場合は対象を区別し、返すconcept IDにbundleの場所を添える。

[OKF Agent Memory](../okf-agent-memory/SKILL.md)の検索・参照手順とCLIの準備を確認する。コマンド書式と実行方法は同スキルに従い、作業ディレクトリは利用先プロジェクトのルートに保つ。この作業は既存文書の検索・参照に限り、bundleの初期化や知識の保存・更新は行わない。

## 2. 候補を選んで本文を読む

1. 作業開始時にルールと原則をそれぞれ全件検索し、すべての `description` を確認する。この候補取得は検索語やパスで狭めない。
2. 依頼、成果物、変更対象、段階を各descriptionと照合し、合致する文書のconcept IDを選ぶ。判断しづらい文書も選び、明らかに対象外の本文は取得しない。
3. 選んだ本文を取得し、適用条件・例外・governanceを確認する。descriptionを読んだだけで本文を確認したことにしない。
4. 対象領域を初めて変更するときは、実際のファイルパスごとに適用文書を検索する。この検索はtypeを絞らず、他の種類に付いた制約も確認する。
5. 段階や範囲が変わったら候補を選び直す。確認済みの本文は、内容が変わった場合や適用の再確認が必要な場合に読み直す。

全件検索の結果が省略された場合は、利用可能な出力の取得方法で残りも確認する。読み取り専用の指定がある場合は、出力の一時保存を含む書き込みを追加しない。

`context` は判断の背景として参照し、`constraint` は条件に該当する制約として扱う。`hold` はOKFの手順に従い、根拠と既存の解除・承認を確認する。適用範囲や矛盾も本文から判断し、文書名や種類だけで操作の許可・禁止を決めない。

## 3. 適用結果を返す

呼び出し元へ、必要な範囲で次を返す。

- 対象bundleと検索した範囲。
- 本文を確認したconcept ID、適用条件、判断を変える制約・原則とその影響。
- 未確認の資料、矛盾、保留事項、取得できなかった理由。

検索が正常終了して0件なら未登録として扱う。bundleがない、CLIが起動できない、出力を最後まで確認できない場合は「制約なし」とせず、確認できた範囲と不足を返す。呼び出し元が必須資料の取得に依存する判断と、独立して進められる作業を分けられるようにする。

文書の名前を並べただけで適用実績とせず、実際の判断に関わる内容を伝える。検索・参照だけの依頼では、この結果を返して終了する。
