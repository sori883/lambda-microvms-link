# コメントの知識をOKFへ残す

対象は依頼されたファイル・差分のコメントと、そこから移す知識である。目的、基準と対象の版、他者の変更、既存のOKF記録を確認する。ソースに残る説明を減らし、後の担当がコードから必要な知識を見つけられるようにする。

## コメントを分類する

周辺のコード・テスト・履歴を読み、説明の内容と必要性を確かめる。背景が不明なら [how](../how/SKILL.md)・[why](../why/SKILL.md)へ対象を絞って調べる。コメントの断言だけで、現在の事実や承認済みのルールと扱わない。

| 分類 | 扱い |
| --- | --- |
| コードを言い換えただけの説明、空の区切り、役目を終えた作業メモ | 必要な意味が失われないことを確認して削除する。価値のない本文をOKFへ量産しない |
| 設計理由、外部制約、回避策の背景、重要な挙動・歴史 | 下の手順でOKFへ保存・照合してから削除する |
| ライセンス・著作権、公開API文書として必要な契約、コンパイラ・ツールが解釈する指示 | ソース上での役割があるため保持する。削除・変更は別途その契約と挙動を確認する |
| 根拠不明、矛盾、保存先や権限の不足 | 保持して未解決とする。分からないことを理由に先に消さない |

lint抑制・型抑制・生成指示などは文章に見えても実行や検証へ影響する。説明部分は保存できるが、指示の削除を通常のコメント削除に含めない。根本修正が必要なコードは箇所と理由を報告し、承認された変更範囲へ引き継ぐ。

## 保存してから削除する

1. [OKFスキル](../okf-agent-memory/SKILL.md)のCLIで既存の同じ対象・責務の知識を探す。既存conceptを更新できるなら再利用する。
2. 現在の振る舞いは `knowledge`、採用理由・見送り理由は `decision`、明示的に合意された制約は `rule` として整理する。単にコメントに書かれていた主張を強制ルールに昇格しない。確度・版・適用条件を残す。
3. `code_refs`に利用先プロジェクト相対のファイルパスまたはglobを設定する。シンボル・該当範囲・参照リビジョンは本文に記す。行番号を `code_refs` のパスへ混ぜない。根拠は `sources`と本文へ残し、元コメントの位置・内容と移した意味の対応を追えるようにする。
4. CLIで保存し、読み返しと形式検証を行う。移行先の本文だけで理由・制約を理解でき、対象コードに対応し、根拠と未確認事項が失われていないことを照合する。保存・照合に失敗したコメントは削除しない。
5. 保存が確認できたコメントだけを削除する。同じファイルの他者の変更は保持する。ソースへ代わりの長い説明やリンクコメントを増やさず、OKFの `code_refs`から関連付ける。
6. 削除後の差分と必要なビルド・型・テスト・文書生成を確認する。コメント以外の構文や公開契約、ツール指示に影響していないか確かめる。影響があれば自分の削除を戻して未完了と記す。先に保存した知識は自動削除しない。

読み取り専用なら分類・移行案だけを返し、保存や削除を行わない。書き込み担当を分ける場合は、保存済みconceptと照合結果を削除担当へ渡す。同じOKF文書へ並行して書かせない。

## 結果を渡す

削除したコメントの位置、保存したconceptと `code_refs`、保存・内容照合・削除後の確認結果を対応付けて返す。保持したコメントの理由、未解決の主張、必要なコード修正を分ける。知識保存だけ終わった状態をコメント整理の完了にしない。
