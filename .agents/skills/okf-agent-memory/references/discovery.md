# 検索・参照

## 検索してから本文を読む

設計判断、既存の要件・規約に関する質問、新しいconceptの作成では、まず関連する語で `search` する。最初は `--limit 3` でタイトルと `description` を確認し、必要なconceptだけ `show` で取得する。候補が足りなければ語を変えるか件数を増やす。

`search` はキーワードの関連度検索やtypeによる絞り込み、`show` は本文・frontmatter・入出方向の関連リンクの取得に使う。本文と直接のリンクで判断できれば、関係する文書すべてを読み込む必要はない。同じ話題が見つかったら、作成ではなく更新を検討する。

検索対象はタイトル・タグ・説明・concept ID・本文。日本語の単語分割と全角・半角などの表記の正規化に対応するため、「認証変更の保留ルール」は「ルール」で検索できる。複数語はいずれかに一致する文書を返す。順位付けや一致方法は [CLIの詳細](cli.md#日本語の検索) を参照する。

## ルールと原則をdescriptionから選ぶ

適用ルールを調べるときは、検索語を付けず `search --type rule "$OKF_BUNDLE" --all --json` で全件取得する。各descriptionを今回の依頼、成果物、変更対象、作業の段階に照らし合わせ、合致する文書を選ぶ。選んだ `concept_id` を `show` に渡し、本文の詳細な適用条件・例外・`governance` を確認する。適用するか判断しづらい文書も本文を読み、明らかに対象外の文書は本文を取得しない。

原則を調べる場合は `search --type principle "$OKF_BUNDLE" --all --json` で同じ手順を使う。作業の段階や対象範囲が変わったら適用判断を見直す。個別文書への固定の対応表を手順に複製しない。

typeだけの検索では、`code_refs` のない全体ルールも取得できる。`hold`、`constraint`、`context` の順にdescriptionを確認する。初回の候補をキーワード、パス、上位件数で狭めない。検索語とtypeの組み合わせは、特定の話題を掘り下げるときに使う。`--all` は件数上限を外すが、実行ツールが出力を省略した場合はファイルに保存して分割して読む。

## 変更するコードから調べる

対象領域を初めて変更する前に、`search --for-path ... --all` で `code_refs` に対応するconceptを取得する。これはキーワードを必要としない逆引きで、`hold`、`constraint`、`context` の順に確認する。ディレクトリだけの検索では拡張子付きglobを拾えないため、実際に変更するファイルのパスでも確認する。

| `governance` | 扱い |
| --- | --- |
| `hold` | 対象操作の保留。文書の適用範囲と解除条件を確認し、ユーザーの明示的な承認なしに対象操作を進めない。既に当該保留を踏まえた承認があれば繰り返し確認しない |
| `constraint` | 対象に適用される行動・禁止事項を守る |
| `context` | 判断の背景として参照する |

省略時は `context`。`rule` というtypeやディレクトリ名だけで強制力を推定しない。`code_refs` のない全体ルールは `search --type rule` で確認する。逆に、パス検索で変更対象の制約を調べるときはtypeを絞らず、`principle` などほかの種類に付いた制約・保留も確認する。

文書が矛盾したら、対象範囲、明示された後継関係、ユーザーの指示を確認する。検索順位や更新日時だけで、どちらが有効か決めない。`draft`・`deprecated`・期限切れを現行の確定事項として扱わず、期限切れだけで制約や保留が解除されたとも判断しない。

## bundleの境界

対象bundleは明示し、別のプロジェクトの知識を混ぜない。kotoの共通知識・原則とプロジェクト固有の知識は、同じ `.space/babel/` から検索する。利用者が別のbundleを指定した場合は、その場所と文書の出所を明示する。

利用先の補足はプロジェクト側に記録する。配布文書そのものの更新を依頼されていなければ、配布元の本文を変更しない。
