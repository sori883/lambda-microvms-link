# 更新・矛盾の扱い

## 同じ文書を更新する

新しい情報が既存conceptと同じ対象・責務に属するなら、`-new` や `-v2` の複製を作らず `update` を使う。更新直前に `show` で現在の内容を取得し、他の作業による変更や独自メタデータを保持する。

本文を変更するときは更新後の本文全体を `--body` で渡す。部分的な追記文を本文全体の置換として渡さない。変更しない項目は省略し、変更内容に合わせて `description` と根拠資料を見直す。

## 訂正と履歴

ユーザーの明示的な訂正を反映し、否定された推測を復活させない。根拠資料と既存の記述が矛盾する場合は、旧情報が誤り・廃止・別条件での事実のどれなのかを確認する。判断できなければ矛盾があることを記録し、解消済みとして上書きしない。

現在の状態を本文の先頭で分かるようにし、旧判断の理由が今後も役立つ場合は経緯として残す。文書自体を廃止する場合は `status: deprecated` とし、後継があればリンクする。期限切れだけを理由に削除せず、未確認のまま `stale_after` を延長しない。

`generated` は内容の更新に合わせて更新する。過去の `verified` を現在日時へ書き換えたり、変更後の内容も人間が確認したと扱ったりしない。確認範囲と再検証の扱いは [frontmatterの定義](frontmatter.md) に従う。

## 物理削除する

文書のファイルを削除する依頼には `delete "concept-id" "$OKF_BUNDLE" --actor "agent:codex" --json` を使う。`--dry-run` で、解除する関連、変更するファイル、新たに孤立する文書を先に確認できる。削除の依頼・承認が既にある場合に、同じ確認を繰り返す必要はない。

CLIは対象ファイル、関連項目、目次を整理し、ログに削除を記録する。通常の文章中のリンクは表示文字を残すため、文章の意味も変更する必要がある場合は別途 `update` する。`sources` や外部文書からの参照など、グラフに含まれない参照は自動では書き換えない。

削除後の孤立文書と、関連解除によって古くなった `verified` はstrict検証に出ることがある。削除成功と検証通過を区別して報告する。詳細な対象範囲と部分失敗時の扱いは [CLIの詳細](cli.md) を参照する。

## 保存後

CLIが更新した目次の説明・変更履歴と、`show` で取得した文書を確認する。影響する関連文書も調べ、必要な変更を行ってから `validate --strict --drift` を通す。検証を通すために出所や過去の検証記録を捏造・削除しない。

途中で失敗した場合は、エラーが指す文書を `show` で確認して書き込み済みの範囲を把握する。同じ操作を無条件に繰り返して履歴やリンクを重複させない。CLIで保存・検証できない操作は未完了として報告する。

本文が正しく保存され、目次だけが同期されていない場合は `update "concept-id" "$OKF_BUNDLE" --sync --json` を使う。内容が変わらなければ `generated` は維持される。書き込み途中の失敗と復旧の制限は [CLIの詳細](cli.md) を参照する。
