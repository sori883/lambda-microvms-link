# frontmatterの定義

このスキルが扱うOKF文書のプロファイルを定義する。5種類の `type` や `title`・`description` の必須化を、OKF全体の制約とは扱わない。

## 項目

| 項目 | 必須・任意 | 形式・扱い |
| --- | --- | --- |
| `type` | 必須 | `rule` / `principle` / `knowledge` / `procedure` / `decision` |
| `title` | 必須 | 空でない文字列。人が読む文書名 |
| `description` | 必須 | 空でない文字列。文書が何を伝えるかを自然言語で1文にする |
| `resource` | 任意 | 文書が説明する対象のURL・パス。対象がなければ省略 |
| `tags` | 任意 | 空でない文字列の配列。重複させない |
| `generated` | 任意 | `{by, at}`。現在の内容を作成・更新した主体と日時。指定時は両方必須 |
| `verified` | 任意 | `{by, at}` の配列。人間による明示的な内容確認を記録し、各要素で両方必須 |
| `sources` | 任意 | 根拠資料の配列。各要素で `resource` 必須 |
| `status` | 任意 | `draft` / `stable` / `deprecated`。省略時は `stable` |
| `stale_after` | 任意 | 鮮度を再確認するタイムゾーン付きISO 8601日時。省略時は期限なし |
| `governance` | 任意 | `constraint` / `hold` / `context`。省略時は `context` |
| `code_refs` | 任意 | 利用先プロジェクトを基準とする相対パス・globの配列 |

本文はfrontmatterに詰め込まず、その後のMarkdownに書く。未指定の任意項目を空文字列や意味のない値で埋めない。更新時には、理解していない独自フィールドも保持する。

`rule` のdescriptionは「いつ適用するか」と「何を守るか」、`principle` は「どの場面で、何を判断の拠り所にするか」が分かる1文にする。検索結果から本文を読む対象を選べるよう、適用場面を明記する。詳細な条件と例外は本文で説明し、descriptionから本文の適用範囲を誤解させない。

## `type` の選び方

| 値 | 保存先 | 意味 |
| --- | --- | --- |
| `rule` | `rules/` | 具体的に守る行動・禁止事項 |
| `principle` | `principles/` | 判断の拠り所になる原則 |
| `knowledge` | `knowledge/` | 事実・構造・背景の説明 |
| `procedure` | `procedures/` | 目的を達成するための手順 |
| `decision` | `decisions/` | 決定と、その理由・経緯 |

同じ本文を複数のtypeに複製しない。例えば、決定の理由は `decision` の本文にまとめ、別のルールから必要に応じてリンクする。`type` は内容の種類、`governance` はエージェントの扱いを指定する別の項目である。

## 作成と検証の記録

エージェントが内容を作成・実質的に更新するときは `generated` を記録する。`by` は実際に分かる主体を使い、モデル名やバージョンを推測しない。例えば `agent:codex`、`human:const`、`process:okf-cli` のように識別する。既存の `codex/<version>` 形式も、根拠があれば保持する。`at` は実際の作成・更新日時とし、例の日時を流用しない。

`verified` は、誰がその内容を確認したかを示す。人間が明示的に確認した内容・範囲を超えて追加しない。「実装してよい」という許可や、自動テストの成功は内容の人間レビューを意味しない。必要なら確認範囲を本文に書く。

内容を変更しても過去の検証日時を現在へ書き換えない。`verified.at` が `generated.at` より古い場合、その記録は変更後の内容を確認した証拠にならない。履歴として保持し、現在の内容は再確認が必要だと区別する。

`status: stable` も人間の検証済みを意味しない。未確定の提案・推測は `draft` とし、本文でも不確実性を明記する。廃止した内容は `deprecated` にして、後継があれば参照する。

## 根拠と対象コード

`resource` は文書が説明する対象、`sources` は記述の根拠、`code_refs` は関連するコード範囲である。対象コードとして関連付けただけでは、そのコードを読んで内容を検証したことにはならない。

`sources` には、実際に確認したソースコード・設計文書・公式資料・参照できるユーザーの決定記録などを挙げる。各要素は次の形を使う。

| 項目 | 扱い |
| --- | --- |
| `resource` | 必須。根拠資料のURL・パス |
| `id` | 任意。文書内で根拠を識別する名前 |
| `title` | 任意。資料のタイトル |
| `author` | 任意。分かっている著者・作成主体 |
| `last_modified` | 任意。分かっている資料の最終更新日時 |
| `usage_count` | 任意。利用回数を管理する場合の0以上の整数 |

ソースコードなら、必要に応じてコミットや該当箇所も本文に記す。ユーザーの発言に参照先がない場合はURLを捏造せず、明示された決定と日付を本文に要約する。最終更新日時や利用回数が分からなければ省略する。

日時は `2026-09-20T10:00:00+09:00` のようにタイムゾーンを含める。`code_refs` は `/` 区切りのプロジェクト相対パスまたはglobで書く。Markdown本文の相対リンクは、その文書ファイルの位置を基準とする。基準が違うので混同しない。

## 目次・履歴

`index.md` と `log.md` は通常のconceptではなく、上記の必須項目を適用しない。bundle直下の `index.md` に `okf_version: "0.2"` を置き、子の目次や履歴にはfrontmatterを付けない。

CLIが親の目次に文書へのリンクと `description` を反映し、履歴に変更を記録する。文書を新規作成・更新する際に、これらを別のconceptとして作成したり、手動で重複追記したりしない。
