# 安全なチェックポイント

会話を知らないエージェントが、保存された状態から作業を再開できるようにする。中断時点の実施内容と未完了事項を区別し、保存結果に基づいて引き継ぐ。

## 起動条件

- ユーザーが作業の中断、引き継ぎ、チェックポイントの保存を明示的に依頼したときに使う。スキルを参照しただけで進行中の作業を止めない。
- 「続けて」「止めないで」「寝るので作業を続けて」という指示では中断しない。「保存して続けて」の場合は記録を保存して作業を続ける。
- コンテキストの縮約に備えて記録する場合も、保存と中断を区別する。中断の依頼がなければ、保存後に元の作業を続ける。

## 1. 安全な区切りで止める

中断する場合は、新しい作業を始めず、実行中の最小の操作を完了させる。編集途中の不整合は最小限の修正で解消するか、自分がその操作で加えた変更だけを安全に戻せる場合に限って戻す。他者や別タスクの変更は保持する。

中断する場合に当該作業のサブエージェントやバックグラウンド処理が動いていれば、新しい処理を始めないよう伝え、安全に停止できる方法で止める。停止結果と書き込み済みの範囲を確認し、他の作業のプロセスには触れない。記録だけを保存して作業を続ける場合は、稼働中の処理を記録して手順2へ進む。

既知の失敗を解消できない場合は、原因・影響範囲・再開時の修復手順を未解決事項として残す。未検証の状態を成功扱いしない。停止を確認できない処理は、まだ稼働している可能性を明記する。

## 2. 再開用の記録を保存する

既定の保存先は、作業対象プロジェクトの `.space/checkpoint/<task>-resume.md`。ユーザーが保存先を指定していれば従う。同じタスクの記録があれば更新し、なければディレクトリとファイルを作る。Issue番号などの安定した識別子を使い、別タスクの記録を上書きしない。

次の情報を、会話の参照なしで再開できる範囲で簡潔に書く。

- 目的、完了条件、ユーザーが指定した作業範囲と制約。
- 更新日時、作業ブランチ、worktreeの場所、記録前のHEAD。
- 実施済みの内容と、現在のファイル・変更の状態。
- 実行した検証と結果、未実行・失敗した検証。その根拠となるファイルやログ。
- 未解決事項、既知の不整合、停止未確認の処理、再開時の注意点。
- 次に行う具体的な操作。再開時の最初の一手を明確にする。
- 関連ファイル、Issue、PR、コミット、既存の判断ログへの参照。

根拠は実際に確認したものだけを記録する。既存の判断ログがあれば参照し、会話全文やコマンド出力を重複転記しない。別の作業でも使う知識は `.space/babel/` の対象だが、中断時に新たな知識整理へ作業を広げない。

## 3. 変更と記録を永続化する

Gitを使うプロジェクトでは、現在のブランチで当該作業の未コミット変更とcheckpointを、内容が分かる1つの `wip:` コミットとして保存する。既に同じ状態が保存済みなら、空のコミットは作らない。

作成前に作業ツリーとステージ済みの差分を確認する。当該作業の変更だけを含め、他者・別タスクの変更や既存のステージ内容を巻き込まない。同じファイルに混在する変更を安全に分離できない場合は、無理にコミットせず、ディスク上の変更を保持して未コミットのパスと理由を記録する。

保存対象への書き込みが続いている場合は、当該処理と保存の区切りを調整する。整合した状態を確認できなければコミットせず、稼働中の処理と記録時点をcheckpointに残す。

既知の失敗が残る場合は、checkpointとコミットメッセージにその状態を明記する。コミット禁止の指示、Git未使用、保存・コミットの失敗がある場合は、実際に保存できた範囲と未保存の内容を区別する。コミットに失敗したら理由をcheckpointに追記し、ファイルの保存を確認する。

中断の依頼だけを根拠に、push・新しいPRの作成・マージ・デプロイは行わない。既存のPRがあっても、更新の権限が増えるとは扱わない。

## 4. 保存状態と再開方法を伝える

記録を読み返し、実際のファイル・検証結果と一致していることを確認する。コミット後はそのIDと作業ツリーの状態を確認し、次を短く報告する。

- どこまで進み、何が未完了か。
- checkpointのパスと、ディスク上に保存できた内容・できなかった内容。
- 作成したコミットID。未コミットの変更があれば、そのパスと理由。
- 再開時に読む記録と、最初に行う操作。

中断時は、元のタスクを完了したとは報告しない。「保存して続けて」の依頼では、保存結果を伝えた後に元の作業へ戻る。
