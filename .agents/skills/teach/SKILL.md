# 仕組みと理由をつなげて説明する

目的は人が理解できることである。対象の変更や文書保存は依頼されている場合だけ行う。

1. 会話から、知りたい対象、利用・変更・レビューなどの目的、既に分かっていることを把握する。理解度を試す質問や不要な聞き取りから始めない。
2. [how](../how/SKILL.md)へ動作の問いを、[why](../why/SKILL.md)へ設計理由の問いを渡す。既存の調査結果は再利用し、小さな問いでは必要な方だけ使う。理由の調査範囲は今回の理解に必要なものへ絞る。
3. 最初に何であるかと今回の要点を短く伝える。その後、利用者の操作から内部で何が起こり、どの問題を解くのかを具体例でつなぐ。関数名の一覧だけにしない。
4. 図が理解を助ける場合は、まず主要な関係を示し、必要に応じて要素や経路を足す。Mermaid等の利用できる手段を選ぶ。毎回の図や画像生成を必須にしない。
5. 質問に答える深さで一度区切り、続く質問に合わせて掘り下げる。一度の説明で完結する依頼なら、必要な内容をまとめて渡す。

whyが区別した確度を保つ。確認された理由、コードからの推論、根拠なしを、分かりやすくするために混同しない。用語は一つの概念に一つを使い、初出で短く説明する。

回答は説明そのものと根拠への参照にする。調査担当を起動した経緯や内部の手順を説明の中心にしない。保存する構成文書が必要な依頼は [system-blueprint](../system-blueprint/SKILL.md)へ渡す。
